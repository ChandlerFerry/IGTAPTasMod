# Offline engine host (enginesim)

Runs the game's own code outside Unity, so route searches run on every CPU core instead of inside the game.
The game (turbo) stays the judge: every offline best is replayed there before it becomes a route. What has diverged
from 1x before, and how it was fixed: [`docs/fidelity-log.md`](../docs/fidelity-log.md).

## How it works

| Piece | Role |
|---|---|
| `Prep/` | Rewrites the installed game's `Assembly-CSharp.dll` (Mono.Cecil) so its Unity/third-party references point at `IGTAP.UnityShim`, empties presentation-only methods (`cuts.txt`), injects the plugin's Harmony hooks as plain calls (`hooks.txt`), and makes the game's mutable statics per thread (below, checked at build time against `static-allow.txt`). `surface` lists every engine member reachable from `entries.txt` (what the shim must implement). |
| `Shim/` | `IGTAP.UnityShim`: the Unity API the game touches. Math types (`Vector2`, `Vector3`, `Mathf`, `Color`, ...) are Unity's own managed code (generated by `tools/sanitize-unity.py`), so float results match bit for bit. `Transform`, `GameObject`, components, `Invoke`, `Physics2D` forward to host backends. |
| `Box2D/` | C# port of Box2D v2 (Unity's classic 2D physics), float math in C++ order, Unity's tunables, exact world `SaveState`/`LoadState` for branching. |
| `Runtime/` | Loads a world export into real game objects (`World`), runs Unity's physics semantics on Box2D (`PhysicsWorld`: fixtures from `Collider2D.GetShapes`, layer/contact masks, raycasts incl. start-in-collider and negative distances, collision/trigger callbacks), steps ticks exactly like `TurboRunner` (`Simulation`), and drives input through the shared `MacroEngine.cs`. `OfflineSolver` is the search itself: worker threads mutate, explore and splice input routes on their own `Simulation`, share the best (course time, then `runTicks`) and hand an archive of explored map cells to the next solve (the plugin's `Solver.cs` only launches `IGTAP.EngineSim.exe solve`). |
| `Cli/` | `IGTAP.EngineSim.exe replay | bench | solve | searchbench | humanize | map | ultras | fulltas | path | rays | probe | clip | lab`. |

Ground truth comes from the plugin (`EngineSimBridge.cs`):

- `POST /api/enginesim/trace {course, capabilities; routeId | ticks, name, world: true, freshStart}` — a
  turbo run from the solver's start state; writes `<name>.json` (start state + full state after every tick) and
  `<name>.world.json` (every GameObject, collider physics shapes, bodies, script fields, statics, Physics2D settings) to
  `BepInEx/config/IGTAPTasMod/enginesim/`. Unity has no shapes for a collider that is off (an unloaded zone, a disabled
  component), so the export copies each off box, capsule, circle, polygon and edge collider onto a live probe at the same
  pose and writes the probe's shapes: the engine needs them when the game turns the collider on (`ZoneLoader` loading a
  zone at a teleporter). Composites and tilemaps have none while off; an older export has none for any off collider.
  The studio maps draw every zone (`Map.OnObjects`). The header says what a run is scored on (`Simulation.SetTarget`):
  `course` (and `gameCourse`, the game's `courseNumber`, when they differ: Courses 11–15 are Courses 1–5 overgrown), a bonus's
  reward box `finish`, and for a transition `transition: true` (timed in physics ticks, `MacroEngine.PhysicsTicks`)
  with an end box `finish` or `finishStart` (the course whose start gate ends it).
- `POST /api/enginesim/submit {course, capabilities; ticks}` — turbo replay of an offline candidate; saved as the
  category's record route (`<course>_<CAPS> <time>`) when it finishes faster than the current best, or as fast in fewer
  physics ticks from the run start (`runTicks`; the saved route is replayed for its own). On a course it is also saved as
  the farm route (`<course>_<CAPS> farm <runTicks × 0.02>`) when it takes fewer `runTicks` than the farm route
  (`farmSaved`). The reply has both times.
- `POST /api/enginesim/raycast {rays: [[ox, oy, dx, dy, distance, mask]...]}` — Unity raycast probes.
- `POST /api/enginesim/ghost {course, capabilities | fulltas, a, b}` and `POST /api/enginesim/slack {name}` —
  read-only, for the studio's ghost compare and humanize slack: two routes' per-tick positions from the `map` JSON on
  disk (with the first tick their bodies part), and a route's human version's slack report (`<best>-human.slack.json`)
  with its input ticks.
- Full-TAS (`docs/fulltas.md`): `POST /api/enginesim/trace {fulltas: <run>}` writes `fulltas-<run>.json` from the fresh
  new game (a `"start": "vman"` run: the Vman speedrun's world) with the run's goals in the header (`fulltas.goals`);
  `IGTAP.EngineSim fulltas <trace>` searches the whole run in windows of goals and sends complete, faster runs to
  `POST /api/fulltas/submit`.

`tools/enginesim-capture.py routes|random|start|route` captures traces; `tools/enginesim-redeploy.py` rebuilds and
reloads the plugin.

## Use

All searching happens here, never in the game (the root `README.md` rules: *Search offline in `enginesim`, never in
the game*). The game is needed once per course/category to capture a start trace and world, and afterwards only to
judge new bests.

```powershell
dotnet build enginesim\Cli\IGTAP.EngineSim.csproj -c Release
$exe = "enginesim\Cli\bin\Release\net10.0\IGTAP.EngineSim.exe"
$traces = "C:\Program Files (x86)\Steam\steamapps\common\IGTAP an Incremental Game That's Also a Platformer\BepInEx\config\IGTAPTasMod\enginesim"
& $exe replay $traces\rand-*.json $traces\route-*.json   # fidelity: first tick where offline != turbo
& $exe bench  $traces\route-c1-none-4.14.json            # single-core speed
& $exe solve  $traces\route-c1-none-4.14.json --threads 16 --minutes 60 --stall-minutes 5
& $exe path   $traces\route-c1-none-4.14.json route.json  # where the course timer starts/stops along a route
& $exe humanize $traces\start-c1-none.json $traces\offline-best\1_none-1.66.json  # same-time, easier version + slack report
& $exe probe  $traces\route-c1-wjds-1.06.json probe.json --out result.json  # one start state, branches of inputs, every tick
```

`solve` loads the trace's world and start state on every thread, seeds with the trace's inputs (plus `--seed` traces),
writes each new best to `<traces>\offline-best\`, and sends each best that beats its seeds to the running game's
`/api/enginesim/submit` (skip with `--no-submit`). Each worker walks its best's plateau: a mutation that finishes
exactly as fast (or rejoins the best's state) replaces it (`drifts` in the progress line), since a faster route is often
several mutations away, each alone no faster. A best is the fastest course time; at the same time, the fewest
physics ticks from the run start (`runTicks`), which shortens a flying start's setup before its last start-gate
crossing (off the timer, but a player still sits through it). The search never finishes a run slower on the course
timer than its best, so it doesn't search for farm routes: those come from the judged candidates. With the game closed
the best stays on disk; the plugin judges every waiting `offline-best\` file that beats or ties the saved route (its
category, then the course's other categories), and the group's file with the fewest `runTicks` when that beats the farm
route, as soon as the game is in the world and idle (a studio Optimize run holds the queue only while it starts
each target, and its running target's own files until that `solve` ends), and moves them to `offline-best\judged\`.

Splicing joins explored segments onto the best (`splices` in the progress line). The best's replay records the course
time and input tick of its first arrival in each map cell. An explore run that reaches one of those cells at least a
tick sooner runs on with the best's inputs from that cell (`Splice`). The jump button's press and release flags are
fixed where the two join. Each new best also tries up to 64 archive cells that are already ahead of it, biggest gain
first, including cells from earlier solves. On Course 4 WJ_DS_DJ this took the best from 16.58 to 15.04 within a
minute: the explore archive held faster segments that the whole-route mutations couldn't reach.

A map cell is a 48×48 square (plus the forced-path boxes passed, or a Full-TAS run's goal progress). Ground-tagged
surfaces refill wall jumps, double jumps and air dashes on every touch; `Moss`-tagged ones refill nothing
(`Movement.touchedMossyGround`; the Overworld's `moss` tilemap and the upgrade trees' `Tree*Ground`). While the last
surface touched is moss, the counts left are part of the cell, so an earlier arrival with fewer left doesn't replace,
cut or splice over a later one that has them (`OfflineSolver.CellKey`). A Full-TAS run's cells always keep the counts
left, and its momentum too, in steps of 250 each way on x and y (`MomentumBucket`): a superjump or spike super carries
its momentum for a hundred ticks, so an arrival that has it and one that doesn't don't replace each other.

The guide (`--guide`, experimental and off by default) weighs each explore pick by how close the cell is to the target:
`guide d=` in the progress line is the best cell's walkable distance to it (`--guide-weight W` how hard it pulls, default
1). On two Course 4 WJ_DS_DJ pairs of 2-minute 8-thread arms it won one and lost one (unseeded: 12.62 vs 11.46 lost;
`--rng 4242`: 11.32 vs 11.90 won; the `--rng 777` pair was cut short), so the default stays the plain search. `--rng N`
seeds the search's randomness, worker `i` getting `N + i`, instead of the clock: two runs with the same seed on one thread
find the same bests in the same order.
The distance comes from a Dijkstra field over the static collision geometry on a 24-unit grid of world cells, flooded from
the target (the course's end gate, a bonus's reward box, a transition's finish box or its finish start's gate, or the
current `at:` goal rect in Full-TAS goal mode, which also replaces its straight-line `GoalDistance`): free where no solid
collider covers a cell's centre, a spike cell six steps. So the number is a heuristic — a mover, a one-way or a coloured
swap is in it only as the world export left it — and the picks keep their pick-count novelty; a wrong number wastes
picks, never a run. The field builds once per world and target, over the region the target and the explored cells cover
(`DistanceField`), and is rebuilt when the static geometry changes (a block swap or a zone load bumps its version).

Tech lives on the ticks where the player's contact changes, and a random burst puts its jump and dash anywhere in its
chunks. So each explore run records its contacts (it leaves the ground at a ledge, lands, touches or leaves a wall,
dies), and half the time one of them gets a graft (`grafts` in the progress line): the run is cut a few ticks around
it, one input made for that contact goes there, then 40 ticks of stick (`OfflineSolver.GraftsAt`):

| Contact | Ticks | Inputs | With the omnidash |
|---|---|---|---|
| leaves the ground (a ledge) | −4..+3 | coyote jump, super off the edge (dash, jump on frame 1–4), backwards dash-jump, jump held into a dash | hyper, ultra, super ground bounce, wavejump, aimed dash |
| lands | −4..+1 | buffered jump, the buffered dash's superjump, jump held into a dash, dash | ground bounce, wave bounce, super ground bounce, hyper |
| touches a wall | −3..+3 | wall jump, superbounce, wall dash, jump held into a dash | aimed dash, ground bounce |
| leaves a wall | 0..+4 | wall coyote jump, dash-jump | aimed dash, wavejump |
| dies (mostly spikes past their grace) | −7..−1 | all the plain ones: spike grace jump, a dash buffered onto a corner's ground gap, a super off a spike wall | any |
| a hyper's flat dash slides off a floor's edge (omnidash only) | −3..+3 around that dash's press | — | corner hyper, corner ultra |
| a wall behind (in the air, not dashing, `Velocity.y` under 580, a wall within 12 u of the back at the ground rays' height) | 0..+24 | wall clip, then more clips | wall clip |
| a wall ahead (in the air, not dashing, a wall within 12 u of the front edge at y − 18, y + 19 or y + 45) | −2..+10 | turn away, then clips | turn away |
| the target course's start gate within 16 u of the hitbox while the timer is off | 0 | 8 gate taps, then clips | gate taps |

The corner hyper contact is seen on every physics step, not only on input ticks, because a dash's ticks consume no input
(`OfflineSolver.RecordSlide`). It fires when a down-diagonal dash has landed (`canHyper`, flat) and is still dashing with
`onGround` held up by coyote frames only. Its graft presses that dash again a few ticks either way with a late jump (dash
frame 4–12), so the landing moves along the corner and the hyper jumps in coyote time past the edge. The corner ultra
also puts a wavedash 8–16 ticks before it, so the corner hyper carries a hyper's momentum as `preDashMomentum`.

Why corners: a dash lands as soon as a ground ray touches the floor. The rays start 18 below the player and reach 22
further, so past an outer corner (the body beyond the edge, a rear ray still over the floor) nothing stops the body. The
landing can sit up to ~12 u below standing height; a floor stops it at ~7. The hyper that follows can then be under
`lastHyperY − 4`: the game's ultra, which adds `preDashMomentum.x`. Only an offline lab shows this so far (issue #12);
the progress line counts these grafts (`grafts (N corner hypers, M wall clips)`).

The wall-behind contact is the GC wall clip (the studio's Tech tab): turn toward a wall at your back and the turned
hitbox's front ground ray (x ∓ 25) starts inside it, which grounds you in mid air while `Velocity.y` is under 200. Its
graft flicks the stick toward the wall (0.3–0.55) with the jump released on that tick (a held jump between 150 and 580 up
is cut to 50), presses the jump with a light flick back (0.3–1) the next tick, then holds the jump with the stick at rest
for 0–26 ticks (`OfflineSolver.WallClip`). A clip is a ground touch: on a Ground-tagged wall it refills air dashes,
double jumps and wall jumps.

Clips come in chains, and the states between them don't survive as cells: a square keeps its earliest arrival, which is
seldom the slow one that stopped with a wall at its back. So a clip graft's run records its own contacts, and the next
wall behind after it gets the next clip, up to four deep, with the stick drifting left, right or at rest after each hold
(`OfflineSolver.ClipChain`). A clip-ready state (a wall behind, as above) is also its own cell (key bits 45–46 in a
course), and an explore that starts in one counts the wall behind as a contact on its first tick.

The wall-ahead contact sets a clip up: the stick turns away from the wall for 1–4 ticks (0.3–1) and rests for 3–30, so
the player drifts to a stop with the wall at its back (under an overhang's corner, as Course 1 NONE does at the pillar's
left face); the chain then clips off it. A wall above the back (the back ray at y + 19 or y + 45 hits it, the one at
y − 18 not yet) gets the same rest with no turn, so the player rises up to it clip-ready.

The start-gate contact is the late gate touch (Tech tab): the timer starts on the first tick the player overlaps the
start gate, so a route can reach the far side of it untimed and brush it at the last moment. Its graft rests from the
contact for 0–20 ticks (a jump pressed at the contact half the time, for a player standing by the gate), taps toward the
gate for 1–2 ticks (0.3–1) and back for 1–2, then rests with the jump as it was; one contact tries 8 of these, each
followed by the clip chain (`OfflineSolver.GateTap`). The progress line counts `clips landed/wall clips`, `set-ups that
reached a wall behind/clip setups` and `gate taps`.

The hand-written grafts aren't the only input: the Tech tab's demos (techs.json) are mined into graft patterns
(`Runtime\TechGrafts.cs`). Each demo replays offline from its start (its category's start trace, its own savestate, a
captured `tech-<id>.json` trace, or a lab map's solved `labmaps\<id>.demo.json` over the trace it was solved in), the
contacts along it are detected with the same detection as above (the shared
`ContactLog`), and the input window around its contacts (10 ticks before to 30 after: stick values, presses/holds/releases,
dash, dash jump, dash turn) becomes a pattern tagged by contact type and the unlocks it needs (its `requires` and omnidash;
a window that presses dash needs the dash). The window nearest the demo's last press, release or dash is its key pattern;
up to 8 contacts make patterns, and each side-tagged one is also offered mirrored for the other side.
`IGTAP.EngineSim techgrafts <traces dir>` lists them per tech. A `solve` grafts them at the same contact kinds alongside the
hand-written ones, jittered ±3 ticks and filtered by the run's category unlocks (`tech grafts` in the progress line); the
hand-written grafts stay. `--no-tech-grafts` turns the mined ones off. Whatever trace is solved, the catalog, the demo
traces, savestates and the cache resolve from the configured traces dir (`tools/gamepaths.py`'s TRACES: the game's config
folder's `enginesim`, when it exists), so a copied trace mines or reads the same patterns as the real folder;
`--tech-dir <dir>` overrides it. The mining is cached in
`<traces>\tech-grafts.cache.json`, keyed by the catalog, the demo files and the engine build (`techgrafts --refresh`
re-mines); a grafted window keeps real button edges at the cut (a press or release as a controller makes them).

Before the timer, a course cell also keeps where the player is going (`OfflineSolver.Motion`, key bits 47–49: vertical
speed below −200, under 200, under 580 or above, and the facing). An untimed set-up is slow on purpose, and without
these bits every state of it lost its square to an earlier arrival going the other way.

How far this gets on Course 1 NONE (seeded with the old 1.62 and a prefix of the 1.40's inputs, 6 threads each): from
the first left-face clip (tick 32) on, the late-gate route comes back in under a minute (1.44); from the second
left-face clip's jump (tick 48), the shelf clip (tick 66) or the drop down the right face (tick 100), at 1.44–1.48
within 6 minutes. From the approach alone (tick 23: jump, turn under the pillar's corner) and from the 1.62 alone, not
in 7 minutes: the first left-face clip is the step the search doesn't find by itself yet. `IGTAP_CLIPLOG=1` prints
where clips land (`CLIPLOG x y timed`), where set-ups
reach a wall behind (`SETUPLOG`) and every new cell (`NEWCELL x y timed grafted`).

On `Test-No-Omni-Skip` from nothing (`--fresh --unsolved`), death grafts alone reached goal 3 in 1:30 on 16 threads,
where the build before them hadn't in 10 minutes; with every contact, 2:34 on 8 threads (one run each).

A solve picks up where the last solve of the same target stopped. Its search state goes to `<traces>\archive\<label>.json`
(`<course>_<caps>`) every minute and when it ends, so a solve the studio stops (it kills the process) loses at most the
last minute. The file holds every explore cell's input prefix with how
often it was picked, plus the plateau (each worker's route as fast as the best, drifted away from the saved one), and
a running count of all runs. The next solve replays the prefixes, split across its workers, to rebuild the cells
(~700k ticks for Course 4 after one session, a few seconds). Well-explored cells keep their picks, so exploration
goes on from the frontier and doesn't start again from the course start. Each worker also starts drifting from a
plateau route instead of the saved route. A plateau route's result is not submitted: its file was written when it
was found. `--fresh` ignores the file for this solve but still overwrites it.

Coordinates: three frames, three types (`Runtime\Frames.cs`), so mixing frames is a compile error. `WorldPos` is the
game world's frame: the scene position minus the game's `FloatingOrigin.currentOrigin`; every position you give or read
(forced-path boxes, `--via`/`--avoid`, the studio map's readout, `path`'s `pos`, `courses.json`, `at:x,y,w,h` goals) is
in it. The game shifts every root object whenever the player strays `Threshold` (17500 in every Overworld export) from
the scene origin, so a capture's scene frame depends on where the game was when it was taken (Course 1's start gate:
scene x -241 in one capture, 2000 in another); the world frame doesn't. `ScenePos` is the scene frame now (transform
positions and raycasts; `ScenePos.From` and `AsVector2` are the only raw-vector escapes, at those Unity API boundaries).
`CapturePos` is the scene frame at the trace's capture. A simulation keeps its capture's origin (`Simulation.Origin`,
the frame of the trace's rects, goals and map cells) and its current one (`Simulation.CurrentOrigin`), converts between
the frames around them (`sim.ToScene`, `sim.ToWorld`, `sim.ToCapture`, `sim.FromCapture`), and reads the player's
position per frame (`Simulation.PlayerWorld`, `Simulation.PlayerAtCapture`); a box is checked against the frame it is
given in. Only the trace files themselves
(samples, the world export, the header's goal rects) stay in their capture's scene frame; each sample carries the
`origin` it was taken at.

Turbo, 1x and the engine all rebase. At 1x `FloatingOrigin.LateUpdate` sees the player past `Threshold` after a
tick's `Update` and starts `MoveOrigin`, which waits for the next physics step (`WaitForFixedUpdate`) and then moves every
root object of the active scene back by the player's scene position and lowers `currentOrigin` by it. It leaves the
scene-frame numbers the game keeps (`lastHyperY`, `courseResetPoint`) alone: that is the Float Ultra (a chained hyper
whose second jump is ~11,700 u under `lastHyperY` after a rebase). Turbo runs the game's own `LateUpdate` after each
tick's `Update` and resumes the coroutine right after the next `Physics2D.Simulate` (`TurboRunner.OriginFrame`,
`ResumeRebase`); a turbo snapshot carries `currentOrigin` and a waiting rebase, and a restore moves the world back to
it (`TurboRunner.PutOrigin`), so every judged run starts where its start was taken (before this, turbo never rebased
while 1x did — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Turbo never rebased*).

The engine does the same (`Simulation.FloatingOriginFrame`, `ResumeRebase`, `MoveWorld`): every transform of the active
scene moves back by the reference (a root's local position with it), `currentOrigin` drops, bodies take their
transforms and body-less colliders rebuild their shapes at the next sync, as Unity's do. A body-less box or capsule is
rebuilt from its own geometry and the moved transform in float math (`PhysicsWorld.MovedShapes`); 590 of 591 boxes and
all 85 capsules match Unity's shapes in a VMAN world exported after a rebase (a child transform moves by the reference
too, which matches Unity's own position for ~90% of children; the rest are an ulp off). A snapshot keeps the list of
rebases, and a restore across one rebuilds the world from the capture's poses (`MaterializeRebases`). Past a rebase the
VMAN run's trace (rebase at tick 1168) and the Float Ultra demo's (three rebases, the ultra at tick 1206 with 2740
momentum) replay with every position and Movement field identical; only the body velocity differs on a few landing ticks
(under 3e-5, the ground-seam noise below). `ultras` models the rebase itself on its placed launches (`Rebases` off
there).

After a rebase the tick's rendered frames end with the player at the step's end moved with the world (`_stepTo`, as
turbo's `Place(player, _stepTo)`), not at the Box2D body, which only follows at the next sync (reading the body there
let a far teleport rebase every tick or two — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Far teleport rebased
every other tick*).

The game's mutable statics (`Singleton<T>.instance`, `VmanScript`'s flags, `globalStats`' dictionaries) are
`[ThreadStatic]` in the engine's copy of the game (`Prep`'s `ThreadStaticFields`), and a thread's `World.Load` sets its
own world's; a `Simulation` runs on the thread that loaded its world, as the shim's backends already required (they
used to be shared by every solver thread — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Statics shared between
solver threads*). The visits map is versioned (`VisitsVersion` 2).

A build-time check (`Prep`'s `StaticAudit`) keeps the split from silently rotting: every static field the rewritten game
writes outside a static constructor, or whose contents it mutates (the shim's own mutable statics too), must be per
thread or listed in `enginesim/static-allow.txt` as `Type::field  # reason`, else `retarget` fails the build listing the
offenders (removing one field's per-thread treatment names it). A listed field stays shared between solver threads, so
each reason says why the world exports agree on its value (every claim checked against the corpus's 225 `*.world.json`)
or why no run reads it: the cash/upgrade localisation tables and the symbol, difficulty and clone-fade settings, the
trip breaker's lambda caches, the shim's layer database and instance-id counter, and the `Physics2D`, `Camera.main` and
`Time` fields nothing writes. `Time.fixedDeltaTime` and `Time.timeScale` (written per world load and by `Movement.Start`)
are `[ThreadStatic]` in the shim itself. Re-check the list on a rebase: a new export that disagrees with an entry breaks
the sharing assumption the entry documents.

A forced path limits which runs count. `--via x0,y0,x1,y1` boxes must hold the player's center, in order, before a
finish counts; a run that enters an `--avoid x0,y0,x1,y1` box is cut. Both are checked on every physics tick, dash
ticks included. The boxes passed so far are part of every explore cell, and before the first finish, cells past more
boxes weigh more. Explore bursts get 25 extra ticks of the same stick and hold, so a run that clears a box while
coasting is saved. The search state goes to `archive\<label>-path-<--path-name>.json`, and bests are the category's as
usual. `Cli\forced-paths.json` holds standing rules that apply to every solve of their course and categories (the
studio's too). Right now it cuts, in every category, everything left of Course 1's wall hanging right of the buy
machines and two boxes on its right, left of Course 2's pillar hanging right of its buy machines, right of its two
rooms' right walls (the corridor joining them), the two rooms themselves and the drop under its start floor, and left
of Course 4's rightmost buy machine; Course 3's right hole in WJ_DS, WJ_DS_DJ and WJ_DS_DJ_BS_OM, which leaves the
top-hole shortcut, plus a wall at the left side of the rightmost buy machine (CashPerLoop) so runs don't wander left
through the machine room and the pocket over Checkpoint (1) right of the climb; everything above Course 5's building roof
(the route goes inside); in Course 5 WJ_DS_DJ and WJ_DS_DJ_BS_OM, runs back right past the course entry and the climb up
through the start room's ceiling hole: that hole is the finish, entered from above, and a run climbing up it never
started the timer; and in Course 5 WJ_DS_DJ only (no orange blocks yet), the far left, the low left corner and
everything below the start floor. Courses 1–5's rules cover WJ_DS_DJ_BS_OM too, and Courses 6–12's cover WJ_DS_DJ_BS
and WJ_DS_DJ_BS_OM. For 5to4 it cuts Course 5's ceiling hole and everything left of its start gate, Courses 1 and 2
right of the pillar over each start gate (runs pass their end gates without entering), and, above Course 3's approach
shaft, everything left of the shaft's left wall.

A rule's `optional` list holds named blocks (`name`, `note`, `avoid`, `via`) that apply only when picked:
`--optional <name>` on `solve` or `map`, or the Optimize panel's "Optional avoid blocks" checkboxes. A block with
`"default": true` is picked unless turned off (`--no-optional <name>`, or unticking its checkbox, which starts ticked);
the Optimize matrix's queue takes each course's defaults. Each set of picked
blocks has its own search state, `archive\<label>-opt-<name>+<name>.json`; the map draws an optional block dashed while
it's off. The studio's course search map edits these rules too: **Draw avoid**, drag a box, and **Add avoid**
(`POST /api/enginesim/avoid {course, capabilities, box, name?, on?, remove?}`) cuts it for every solve the map's rules
cover; named, it becomes one such optional block (`"default": true` with "on by default"), created on the rule covering
the map's category (a rule is drawn for the course's categories when none covers it). **Remove** under the map takes a
box back out of the rules' standing avoids and optional blocks, dropping blocks left without boxes. Course 1 has
`avoid-forwards` (x 2436 to 2522, y -361 to -180), `avoid-backwards` (x 2168.3 to 2347.6, y

## Search bench

Search changes are judged on a suite, over several seeds, not on one run: a single `solve` is mostly seed noise (issue
#18). A search change stays on by default only if its median beats the current solver's on the suite.

```powershell
& $exe solve $traces\start-c4-wjdsdj.json --no-submit --fresh --rng 1 --log-json bests.jsonl
& $exe searchbench enginesim\Cli\searchbench-suite.json --seeds 5 --minutes 2 --threads 8 --arms '{"base": [], "guide": ["--guide"]}'
```

- `solve --log-json <file>` writes one JSON line per new best: `wall` (seconds since the search started), `time`,
  `runTicks`, `ticks` (physics ticks simulated so far, all threads) and `how`. `--no-humanize` skips the background
  humanize (the bench passes it, so humanize doesn't take CPU from the search); `--tech-cache <file>` puts the tech
  grafts' mining cache there instead of the traces dir.
- `searchbench <suite.json> [--seeds N] [--minutes M] [--threads T] [--arms {name: [solve args]}] [--traces dir]
  [--out file] [--keep]` runs `solve <copy> --rng s --no-submit --fresh --no-humanize` for every suite course, arm and
  seed `s` = 1..N, one after the other, each as a child process on its own temp copy of the start trace and world
  (`%TEMP%\igtap-searchbench-<time>\<course>\<arm>\seed<s>`), so its `archive\`, `offline-best\` and everything else it
  writes stay there. The bench copies the traces dir's `tech-grafts.cache.json` once into its own folder and every run
  uses that copy (a build change re-mines it there), so nothing is written to the traces dir. `--arms` is JSON or a
  file holding it (default `{"default": []}`); a suite course's `args` go before the arm's. It prints and writes
  (`--out`, default `searchbench.json` in the bench folder) per course and arm the median, min and max over the seeds
  of: wall seconds to the first finish, wall seconds to the course's `target` time (at or under), and the final best;
  a run that never got there counts as never (`-`, above every number), so a `-` median means half the runs or more
  missed it. Each run's best lines are in the output too. The run folders are deleted unless `--keep`.
- `Cli\searchbench-suite.json`: Course 4 `WJ_DS_DJ` (`start-c4-wjdsdj.json`, target 11.24), Course 1 `NONE` (the clip

## Probe

`probe <trace.json> <probe.json> [--out file]` tests exact inputs from one state and logs every physics tick of each
branch: position (world frame), `Velocity`, `momentum`, body velocity, ground/wall, cutscene mode, dash state and
direction, facing, plus any Movement fields listed in `fields`.

```json
{
  "start": { "savestate": "C:/.../savestates/<id>.json", "position": [3028.1, -245], "velocity": [0, 0], "scaleX": 1,
             "fields": { "facingRight": true, "airDashesLeft": 1 } },
  "prefix": [ { "x": 1, "held": false, "press": false, "release": false, "dash": false, "dashJump": 0 } ],
  "branches": [ { "name": "dash+jump", "ticks": [ ... ] } ],
  "extraTicks": 30, "fields": [ "wallJumpsLeft" ]
}
```

Every key is optional. `start` changes the trace's start state before the run: a studio savestate (its world position
is its scene position minus the FloatingOrigin it recorded, so savestates captured before the plugin recorded it are
refused), then a world-frame `position`/`velocity`, `scaleX` and Movement fields by name. Every branch runs `prefix`
then its own ticks; with no branches the prefix runs alone.

Every run models 1x with the player body's interpolation on, on playback's fixed clock (`MacroEngine.FrameGrid` at
`MacroEngine.PlaybackFrameRate`, as turbo does): before each `FixedUpdate` the transform holds the last frame's blend
of the body's last two positions (`Simulation.LagForFixedUpdate`), and after the step every frame between two ticks
runs `Movement.Update` at its blend, a dash freeze's frames first (`InterpolatedFrames`; `hooks.txt` reports the
`TimeStop` call, whose body stays cut). A step-up in any frame moves the body there. Checked against the plugin's 1x
probe: Test-No-Omni-Skip's 7.92 inputs at 280 fps (90 ticks, within 0.001, both dying at action 14) and a Course 1
route at 240 fps (a dash freeze of 12 frames and a step-up, tick for tick).

The in-game counterpart is the plugin's 1x probe (`ProbeRunner.cs`): `POST /api/probe/run {name, route: "1_WJ_DS",
savestateId?, ticks, captureAt?, fps?, omniDash?, pauseAt?, pauseOffset?, pauseFrames?}` plays the ticks at normal speed from the category's quick restart
(a Full-TAS run's `route: "fulltas/VMAN_NONE"`: from a new game of that run; or the savestate) and writes
`BepInEx/config/IGTAPTasMod/probes/<name>.json`: one row per physics tick (`kind: "tick"`) and one per rendered frame
(`kind: "frame"`, with `timeScale`, so a TimeStop's frames show as `timeScale` 0). Positions are in the world frame; each
row also has the FloatingOrigin (`originX/Y`), `lastHyperY` (scene frame: world y + `originY`), the game time (`time`),
the camera (`camX/Y` in the world frame, `camSize`) and Cash (`cash`). `captureAt`
saves a studio savestate (`probe/<name> @<tick>`, with its FloatingOrigin) after that input tick, the start for later
probes there. `pauseAt` opens the pause menu (`pauseMenuScript.menuButtonPressed`, what the Pause button calls) right
after that physics tick, or `pauseOffset` `Movement.Update` frames after it, and `pauseFrames` closes it after that many
frames (rows have `paused`): `timeScale` is 0 and no FixedUpdate runs, but Update's step-up runs every frame
(`tools/probe.py --pause-at --pause-offset --pause-frames`).
A probe's ticks can also carry a route's own pause (`pause`, `pauseTick`, `pauseFrame`: `MacroStep.pauseFrames`), which turbo
and enginesim model too (`MacroEngine.FrameRepeats`, `Simulation.InterpolatedFrames`); `pauseAt`/`pauseOffset` are 1x only. Offline
`probe` takes `base` (inputs played once, unlogged, as every branch's start) and `frames: true` (a row per rendered frame:
`kind` `frame`, its `alpha`, `still` in a freeze or pause). Playback runs on a fixed clock at 280 fps with
vsync off (`TasPlugin.PacePlayback`); `fps` sets that rate instead (turbo and enginesim model 280). Keep
it at 50 or more: playback runs at most one physics tick per frame (`Time.maximumDeltaTime`), so below 50 the game slows
down. `GET /api/probe/status` says whether one is running and the last file written. `fields` (Movement field names)
adds those fields to every row, as `probe`'s `fields` do; every row also lists the zip movers within 300 u (`movers`: world
position and `layer`, 7 Ground, 0 while `MakeIntangible` holds it).

Every position write in `Movement.FixedUpdate` (a jump's `+2`/`+5`, a wall jump's `+1`, the dash's `−20`) starts from
the transform, which holds the last rendered frame's blend of the body's last two positions, so each one pulls the
body back by that frame's lag. On the wall clock the lag changes from run to run, and so does the route; playback's
fixed clock pins it: every frame's game time is a step on a grid half a frame off the physics tick
(`TasPlugin.FixedClockStep`, `Time.captureDeltaTime`). Three scripts read the wall clock, which `captureDeltaTime`
leaves alone (`TasPlugin.PatchWallClock`); during playback they read the fixed clock's frame and its running total
instead: `Movement.TimeStop`'s freeze (so a freeze always runs the same number of `Update` frames),
`cameraMover.LateUpdate` (the camera decides which clones are on screen, `clonesLoD`, and so how they pay) and
`ObjectBobber`. A playback starts with the camera settled on the player (`SavestateService.SnapCamera`). `timer`'s
play-time display still counts the wall clock.

A write from a physics callback inside the step moves the body at once and drops the interpolation: a sideways spring
(`SpringScript.OnTriggerStay2D` → `Movement.hitSpring`, `transform.position += up * 10f`). Turbo syncs it right after
`Physics2D.Simulate` when the transform has moved off the body (`TurboRunner`), and the engine does the same when the
player's transform is dirty after `Physics.Simulate` (`Simulation.Run`) (before this both dropped the push, and a
sideways spring came out 10 u short of 1x — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Sideways spring lost
its push*).

`POST /api/savestates/place {name?, from?, x?, y?, vx?, vy?, facing?, fields?}` makes a probe start anywhere, inside a
wall too: a copy of a studio savestate (`from`) or of the player now, with the world-frame position, `Velocity` (the body
gets `Velocity + momentum`), facing (±1) and any Movement fields (`{"OnWall": true, "wallCoyoteFrames": 7}`) replaced. It
is saved as `lab/<name>` and returns its `id` for `savestateId`. A lab start is for experiments, never a route's.

## Lab maps

`labmaps/<id>.json` is a lab map: a custom level piece injected additively into a world's empty space to demonstrate one tech
exactly — a coyote jump off a plain ledge where no course has a clean one. Shapes (box, polygon, edge) sit relative to an
anchor in the world frame, with a Unity layer and tag (`Ground` refills jumps and dashes on touch, `Moss` refills nothing,
`"spike": true` adds the game's `spikeScript`), then the player's start (position, velocity, facing, Movement fields), a
finish box, `category` (the unlocks its demo runs with) and `tech`/`techNote` (the tech it demonstrates). The repo's
`labmaps/` seeds the config folder's like techs.json.

- `lab space <trace | trace.world.json> [w h] [--route <trace>]... [--list N] [--lab <labmap.json>] [--index N]` lists the
  empty rectangles at least `w x h` in the world frame: no collider, trigger or zone geometry at all (the world export, off
  colliders and every zone's included, so the region is the same whatever is loaded), ranked by distance from the routes'
  paths. `--lab` records the best one (or `--index N`) as the lab map's `anchor` and `region`.
- `lab solve <trace> <labmap.json> [--max-ticks N] [--threads N] [--out <file>] [--exact] [--forbid-jump-not-grounded]` injects
  the lab into the trace's world (static colliders on the ground body, correct layer and tag, before the `Simulation` is built),
  puts the player at the lab start and searches for the minimum-tick human-legal input sequence to the finish box: exhaustive
  breadth-first over the input alphabet (stick x −1/−0.55/0/0.55/1, y −1/0/1, the jump button's press/hold/release by its state,
  a dash with any dash-jump frame 0–12; a dash press is pruned when the run can never dash) and bounded by the first finish —
  every state below the bound is explored to prove the bound is the minimum. Two admissible prunes cut provably dead states: one
  whose highest reachable y (the ballistic arc plus every jump and boost still in reach) is below the finish box, and one too far
  from the box to reach it in the ticks left (the game's own 100 u/step max translation is the most any input can move the
  player). States are deduplicated by a key of the state; the default key is coarse (1 u position, 10 u/s velocity, 1 u counters)
  and gives a demo fast as an upper bound, and `--exact` deduplicates on the bit-exact state (position, velocity, momentum, body
  and every Movement field as their float bits), which proves the bound is the true minimum (or finds a shorter demo). One world
  and `Simulation` per worker thread (the game's statics are per thread); each extension replays the node's input path from the
  lab start in one run. The demo goes to `labmaps/<id>.demo.json` (`inputs`: trace `inputs` ticks; `solvedIn`: the trace whose
  world it was solved in; `search`: states, extensions, the bound, the key mode, the prune counts and the tech the demo
  performs), verified by one replay to the same tick and by the tech's own Movement state on the jump tick (a coyote jump's
  `onGround` held with `coyoteFrames` counting, the dash boost's 730 up + 410 up momentum within `dashBoostMax` of a dash).
  `--forbid-jump-not-grounded` is the negative control: no jump press (nor a dash-jump frame) unless the state is on solid
  ground, and a lab whose start can only jump its own tech then has no solution at all — which is what makes the demo the tech
  and not a hop. `lab replay <trace> <labmap.json> <demo.json>` plays one demo from the lab start, tick by tick. The demo
  also carries its ghost path (`path`: `[x, y, facing]` relative to the anchor at the lab start and after every physics tick,
  on 150 ticks (3 s) past the finish with the stick held full the way the dot faces there). The ghost holds jump from the
  demo's first press on (no release, so no jump cut: the full-height jump), so its arc shows the most the tech's jump buys,
  not the demo's own minimum-tick inputs; `lab replay ... --write-path` rewrites it after the lab moves or for a demo solved
  before demos had one.
- In game (`LabMapService.cs`): `POST /api/labmap/inject {id}` builds one root of colliders at the anchor (world frame through
  `FloatingOrigin.currentOrigin`, BoxCollider2D/PolygonCollider2D/EdgeCollider2D with the layer and tag), `POST
  /api/labmap/restore` destroys it and puts back anything the session touched (the player included), `GET /api/labmap/status`
  says what is injected. A tech with `labmap: <id>` (techs.json) plays its demo on the injected lab: inject, the player at the
  lab start (the lab savestate `place` mechanism — the demo route's `savestateId` is that `lab/labmap-<id>` savestate), the
  demo inputs, then restore at playback end and on a scene change. While a lab map is injected the game never autosaves and
  `SaveSolverRoute` refuses: a lab is lab-only, never a route and never on a route's path (root `README.md` `### Rules`).
  `POST /api/enginesim/trace {tech}` captures a lab demo the same way, so its world export carries the injected geometry and
  `replay` (and `python tools/tech-check.py <id>`) need no injection of their own.
  `POST /api/labmap/inject {id, place: true}` is hand play: it also builds the lab's `hand.shapes` (a floor to stand on, never
  in a demo or `lab solve`, which ignore `hand`) and puts the player at `hand.start` (else `start`) with the lab's `category`
  unlocks; a death or quick restart respawns there (`respawnPoint`). The placed state isn't kept as a savestate, and restore
  puts the unlocks, the course reset point and the respawn point back too. A demo re-injects its lab without the hand shapes.
  The shapes are drawn in game (ground dark with a cyan outline, spikes red, triggers purple, moss green; the finish box
  isn't drawn), unlit, above the level. The studio's Tech tab lists every lab map (`labmaps/*.json`, the config
  folder's and the plugin's embedded ones; a config copy wins, so delete a stale one after editing the repo's) with **Load
  lab** / **Back to start** / **Unload**, and a tech card with a lab map has the same buttons. Both labs sit at anchor
  (-1333, -10585). In hand play a lab whose demo has a `path` draws it as a faint line and replays it with a see-through
  copy of the player's sprites (the ghost: one path point per physics tick, interpolated, held 25 ticks at the end, then
  looped); the studio's lab preview draws the same path dashed.

## Humanize

A best comes out of the search full of tick-exact and analog-exact inputs, most of which don't matter.
`humanize <start-trace> <best.json>` writes `<best>-human.json`, a same-time version that is easier to play,
`<best>-human.md`, which says how much slack each of its inputs has, and `<best>-human.slack.json`, the same slack
structured for the studio (below). `solve` does this for every new best on one
background thread (a newer best replaces one still waiting; the last one is finished before `solve` exits, on the
solve's `--threads` workers once the search has stopped, since its tolerance runs are independent).

Simplify: greedy passes, repeated until none changes anything. A change stays only if the run still finishes offline in
the same time (the course timer, or physics ticks for a bonus or transition), in no more physics ticks from the run
start, and on the forced path (`--via`/`--avoid` plus `Cli\forced-paths.json`, as in `solve`).

- A partial `x` goes to full tilt, else to rest.
- A partial that has to stay goes to the middle of the band of partials (0.3..0.8 in steps of 0.05) that work.
- A stick run takes its neighbour's value, which removes a stick change. A vertical goes back to rest first, and leaves
  rest only to fill a gap in one hold.
- Presses and dashes that change nothing are dropped. Dropping a press after the button was up drops its hold and
  the release that ended it.
- Presses and dashes move as early as they still work (the buffer).

Report: every input of the human version (stick change, jump press, release, dash) is moved up to 6 input ticks
either way, one tick at a time, until it stops working. A stick run also tries the other stick values: `x` full
either way, rest, and every partial on its side; `y` −1, 0, 1. Each input is `exact` (one tick only, or one partial
value only), `free` (no limit found either way, any value), or `window N`. The report counts exact inputs in the
best and in the human version, and lists what changed. Ticks are input ticks (dash and spring ticks take none).

`<best>-human.slack.json` is that report as data: `course`, `capabilities`, `source`, `human`, `time`, `runTicks`, the
counts `exact`/`exactBefore`, and one entry per input of the human version (`tick`, `end`, `kind` (`stickX`, `stickY`,
`press`, `release`, `dash`), `value`, `class`, `window`; `end` is the tick after the input's last). The studio's
**Timeline** tab draws it as the human version's frame timeline (**Human version · input slack**, every frame colored by
the slack of the input on it: red `exact` — practice that one — amber `window`, violet `band`, green `free`), served by
`POST /api/enginesim/slack {name}` with the human version's `ticks`.

The human version is never a record and never replaces the best: it goes to its own file, a change that made it slower
in time or physics ticks is never kept, and the plugin never judges a `-human.json` file. The studio plays the newest one
for the category with "Play human version" (`/api/enginesim/play {human: true}`), and "Walk route" plays the newest
one as fast as the selected route (same game time for a category route, same physics ticks for a farm route) in its
place; while it plays, the studio's top bar turns violet with a HUMANIZED badge (`/api/state` `humanPlayback`).

## Rules

- Nothing here changes how the game or the plugin behave; the plugin only gained read-only export endpoints and
  `submit`, which judges an offline best in turbo: the game replays the candidate's inputs on its own turbo engine
  (`Solver.cs` `Evaluate`), and the run is saved only when it beats the saved route's time or the farm route's
  `runTicks` (`EngineSimBridge.Judge`) — the same check every waiting `offline-best\` file gets.
- A method goes into `cuts.txt` only if it is presentation or real-time-only work that turbo never sees within a run.
- Invokes: every script's `Invoke` fires on ticks, in turbo and here.
- Fidelity is measured, not assumed: `replay` must report every tick identical on the trace corpus.

## Fidelity facts (all verified against traces)

- Game float math is Mono double precision: intermediates in double, rounded on store (`-0.3f*46f*10f/4.5f` =
  -30.666668). `Prep/MonoFloat.cs` widens float loads in Assembly-CSharp and in the shim's math types.
- Colliders: exact shapes from `Collider2D.GetShapes`; static colliders are world-space fixtures on one ground body;
  polygon radius = `defaultContactOffset` 0.01, linearSlop 0.005; Unity `maxTranslationSpeed` 100 = b2_maxTranslation
  per step; contact masks = `(layerMatrix[layer] | include) & ~exclude`, both sides must accept.
- Callbacks: collisions from Box2D touching flags (start of step); triggers from an overlap test after the step, and a
  trigger the pair wasn't touching also enters when its sensor contact touched at the start of the step (a wall jump's
  push into a wall that the step undoes still enters the checkpoint behind it); Enter on the first step, Stay after; the
  start state primes existing contacts as already touching.
- Contact order (Box2D 2.3.x, Unity's lineage, not the 2.4.1 port's): new broadphase pairs are sorted by proxy id
  before their contacts are created; the world contact list is oldest first (Collide order, and the first of equally
  early TOI hits wins); a body's contact list is newest first (the island solver's order). A collider pair's contacts
  (`Collision2D`, `GetContact(0).normal` decides a head bump) are a list: a contact that starts touching goes to the
  end, one that stops is replaced by the last. All of it decides a player wedged in a corner of one composite
  collider to the last bit (`diverge-c5-13.14`: [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Corner wedge
  contact order*).
- Turbo restores (`TurboRunner.Restore`) match that priming: one muted physics step at the restored pose rebuilds
  Unity's contacts, so the first tick reports Stay, not a stale Exit plus a fresh Enter (without it, a start touching a
  collider ran differently in turbo from run to run: [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Restores
  without contact priming*).
- A trace start's pending Invokes (`endRecentJump`, the buffer cancels) are due counted from the start's next tick, in
  turbo's snapshot and in `Simulation.LoadStart` alike (it used to count one tick less:
  [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Trace start Invokes one tick early*).
- A turbo snapshot keeps every active-scene object's on/off state (`TurboRunner.Scene.objects`), each clonesScript's
  best path arrays and `globalStats.visitedTeleporters`, and a new game's start is never taken while a zip mover's
  `reset` is on. `ObjectBobber.OnEnable` draws UnityEngine.Random, and `buystatue` turns the statue's
  `StatuePrestigeText` on (a run that bought the statue once left it on:
  [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Statue text left on*). A Full-TAS trace exports its world after
  restoring the start (`FullTasTrace`).
- Clones step in scene-load order, instance id highest first, in turbo (`TurboRunner.Run`) and here (`Economy`) alike.
  Two courses spawning on one tick take their fast/big rolls in that order (turbo used `FindObjectsSortMode.None`
  before: [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Clone order changed between sessions*). Instance ids keep their
  relative order from load to load. 1x playback runs `clonesScript.Update` in Unity's own order, once per rendered frame
  (Δt 1/280): neither is proven to match yet.
- `replay` names the first tick Cash, the RNG and Cash by 1 W or more split (`first split`), past the 60 differences
  it lists. Cash here is start − spent + awarded + earned, the game's a running total: they differ in the last bit
  (tick 13336 above), which only matters for a purchase within a rounding of its cost.
- Turbo spawns no floating numbers (`FloatingNumberScript.ActuallySpawnText` off for the run) — a long replay once
  drained their pool of 200 ([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Floating number pool drained*).
- Raycasts: direction normalized, negative distance flips the ray, start-inside hits at fraction 0 with normal −dir,
  triggers are hit (`queriesHitTriggers`), and the nearest hit wins across a composite's shapes too (the port's
  tree walk once returned the last shape in tree order:
  [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Raycast tree walk returned the last shape*).
- `Collider2D.Distance` is negative for overlapping colliders (the depth that separates them: separating-axis over the
  shapes' faces, minus both radii), as in Unity; GJK alone stops at 0. Movement's squish check (`distance <
  squishDistance`, −20, for `SquishGraceFrames` + 1 ticks) is its only caller (a VMAN dash died squished in turbo and
  ran on offline: [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Squish death on the VMAN wall*).
- Transforms: the player's parent (`PlayerObject`) follows the game's `FloatingOrigin` and sits at (−20200, −10539)
  on Course 4. Unity keeps only the local position, so a world position reads back as parent + (world − parent),
  rounded (20202.4453 → 20202.4434), while the body keeps the unrounded value. A scale change (facing flip) rebuilds
  the shapes but does not move the body; a position/rotation write does.
- Presses: the game takes them only in `Movement.Update`, never inside a `FixedUpdate`, so a route's presses go in at
  the tick start (`MacroEngine.BeforeTick`: the plugin's `FixedUpdate` prefix, offline before `FixedUpdate`, both after
  the pending Invokes), not at the input hook, where the game already read the buttons (Movement.cs:1033-1056). A dash
  that hits a wall takes its input tick in that tick after all; its presses go in at the wall branch's first call
  (`MacroEngine.WallTouch`: a `touchedSolidGround`/`touchedMossyGround` prefix) — traces captured before this pressed
  at the hook ([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Presses at the input hook*).
- The stick: `Movement.FixedUpdate` reads the controller (`NormaliseInput(moveAction.ReadValue<Vector2>())`,
  Movement.cs:872) before the input hook, and fast fall (stick down: gravity ×1.4 while the body rises slower than 300,
  and a 1.4× fall speed cap, Movement.cs:1104-1128) and wall-slide speed (down ×1.5, up ×0.35,
  `ApplyWallslideFriction`) use that read, not the hook's `MoveAxis`. A run's stick reaches it through
  `MacroEngine.TickStick` (the plugin: a `NormaliseInput` prefix; offline: the shim's `InputAction.ReadValue`): the
  vertical of the input tick due next with x at rest, or on a tick in a dash or spring lock (no hook) the stick the last
  input tick held for the lock (`lockMoveX/lockMoveY`; unset: x at rest, y of the next input tick). That x is a super
  jump's direction (`CheckForSuperJump`).
- Dash turn: a dash started with no sideways stick (with the omnidash: with the stick at rest) goes the way the player
  faces and waits for one (`WaitingForDashInput`): every `Movement.Update` until the next FixedUpdate turns it to the
  stick (Movement.cs:817-834), the last one winning. At 1x and in turbo and offline alike those are the dash freeze's
  frames and the tick's grid frames (`MacroEngine.FrameGrid`). A dash tick's `turnX`/`turnY`
  (`MacroStep.dashTurnX`/`dashTurnY`) is the stick held then: `MacroEngine` arms it after the FixedUpdate the dash
  started in and `StickFor` returns it for those reads only (`BeforeTick` of the next tick disarms it). Unset, the window
  reads the dash tick's own stick. Without the omnidash `Update` drops the vertical; with it the stick is not snapped as a
  pressed dash's is, so sideways 0.3-0.4 and a full vertical aim it 17-22° off vertical (the Freeze aim). It is legal
  (README `### Rules`); the Inwall wallbounce tech demo uses `turnX`. The solver tries it as the omnidash kind `steep`
  ((±0.35, ±0.94) on a dash pressed at rest).
- Zip movers (`PlatformMover`, locked or not): a jump or wall jump while touching one calls `MakeIntangible` (through
  `Movement.MovingPlatformMomentumInherit`), which moves it to the Default layer and back to Ground after
  `WaitForSeconds(0.15)`; the ground and wall rays (Ground only) miss it meanwhile and the normal hitbox (it excludes
  Default) passes into it, while the 40×54 hurtbox still collides. Its other coroutines (`PlayerExit`'s contact clear two
  physics steps after the player leaves, the move once `zipMoversUnlocked`) are gameplay too. Turbo and the engine step
  them on the run's ticks (`TurboRunner` and `Scheduler`: `WaitForSeconds` at the start of the tick an Invoke of that
  delay fires, `WaitForFixedUpdate` right after the next physics step, `null` after `Update`, `WaitForEndOfFrame` at the
  tick's end); snapshots keep the parked iterators, the movers' fields and layers. A layer write rebuilds that object's
  colliders (`PhysicsWorld.LayerChanged`) (before, layers were read once at load and the coroutine never resumed within
  a run: [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Layers read once at load*). Other scripts' coroutines still run to their first yield only. At 1x the Ground layer comes back
  on the first rendered frame 0.15 s after the jump's frame, 0.01 s before the 8th tick after it: in 1x probes on Course
  9's pillar it was back for that tick 8 times in 12 and a tick later the other 4 (frame pacing, a dash freeze right
  after the jump). Turbo and the engine take the 8th tick; a route that needs the block back on exactly that tick can
  desync at playback. The `zip-mover-intangibility` demo shows it. A zone load while a mover is intangible (Unity stops

## Memory

A snapshot (for branching) is ~25 KB on the VMAN route: the broadphase tree stores only nodes that
differ from a shared base, the pair/move buffers only their live prefix, and unchanged fixture records are shared
between snapshots. So are the field captures of the touched scripts and the courses: a capture reuses the previous
one's array while none of its fields changed (`Simulation.CaptureShared`, `FieldState.Matches`) — before, every touched
script's capture was copied into every snapshot, and a VMAN search with 28 workers ran out of memory within minutes
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Field captures copied into every snapshot*). `solve` prints heap and working set every 10 s, and the host
runs with `System.GC.HeapHardLimit` at 70 GiB, so a leak throws OutOfMemory instead of paging the machine.

A best's replay (on every new best, adopted best and plateau drift) keeps a snapshot every 16 input ticks, not every
tick (`OfflineSolver.StateEvery`); a mutation resumes from the one at or before its first changed tick (snapshotting
every tick left the workers waiting on the GC most of the time:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *Snapshot every tick stalled the workers*). A mutation's replay starts from the snapshot it resumed from and
copies the best's record before it (`OfflineSolver.Worker.Replay.CopyPrefix`): same inputs up to there, same states.

The explore archive is one map shared by every worker (`OfflineSolver._archive`): a cell is its input prefix (the run's
inputs and the tick), the arrival time, the picks and the cell it was explored from (`Parent`), never a snapshot. A
snapshot belongs to one worker's `Simulation` (it holds that world's objects and fixtures), so each worker keeps its
own snapshots (`StatesPerWorker`: half the GC heap limit over 32 KB per snapshot, split across the workers), evicted by
the draw pool's pick weight first and recency second, so the frontier's hot cells stay through a wide draw's churn
(plain LRU let them go). A worker that picks a cell it has no snapshot for replays the cell's inputs from its nearest
ancestor it has one for (from the start when none), and keeps a snapshot of every cell on that path. So an explore
draws up to three cells and takes the first it has a snapshot for (`CachedDraws`): on C4 WJ_DS_DJ with 32 threads the
replays were ~23% of all ticks simulated (each worker used to keep its own archive with a snapshot per cell:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *A snapshot per cell per worker*). `solve` and `fulltas` print the archive's size, the share of picks whose snapshot was
cached and the ticks spent replaying (`ArchiveStatus`).

A Full-TAS run's goal-boundary states also persist to disk (`SnapshotStore`, `SnapshotIndex`): when the run first
reaches goal k, or a better arrival does, its state goes to `archive\fulltas-<run>\states\`, keyed by the hash of the
run's inputs up to it and dropped with the archive (the run's `start.key`). A solve's windows start from the stored
state at their prefix's end instead of replaying the run up to there, and a cell replays its prefix from the later of
its worker's own ancestor and a stored goal state on the same inputs (`ArchiveStatus` counts those resumes). A state is
a byte-for-byte value walk of the snapshot (`SimSnapshot`'s fields, world objects as their export's ids, fixtures as
their collider and shape), so a restored one continues exactly as the replayed one; what the walk can't write (a type
it doesn't know) just isn't stored and the run replays to it as before. On the VMAN route a state is ~1.6 MB on disk
(the broadphase tree's shared base is a full copy per state) against ~25 KB in memory.

The physics backing those states rely on: a fixture's shape fingerprint is a plain deterministic mix
(`PhysicsWorld.FingerprintOf`), `Pristine` is the fixtures the world loaded (`ColliderState.Tracked` marks the rebuilds
that join `_changed`), and a capture after a restore re-derives its changed-collider list
(`PhysicsWorld._changedCapture`). Storing states across runs needed all three
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Persisted states across runs*).

Scene queries (raycasts, point tests, `Collider2D.Distance`) read static shapes from a grid built once over the world. A
collider whose static fixtures change, or whose static body moves, is regridded alone at the next query (the whole
grid used to rebuild on each change, with the LOH garbage stalling every worker:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *Grid rebuilt on every change*).
