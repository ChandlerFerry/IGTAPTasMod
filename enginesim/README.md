# Offline engine host (enginesim)

Runs the game's own code outside Unity, so route searches run on every CPU core instead of inside the game.
The game (turbo) stays the judge: every offline best is replayed there before it becomes a route. What has diverged
from 1x before, and how it was fixed: [`docs/fidelity-log.md`](../docs/fidelity-log.md).

## How it works

| Piece | Role |
|---|---|
| `Prep/` | Rewrites the installed game's `Assembly-CSharp.dll` (Mono.Cecil) so its Unity/third-party references point at `IGTAP.UnityShim`, empties presentation-only methods (`cuts.txt`), injects the plugin's Harmony hooks as plain calls (`hooks.txt`), and makes the game's mutable statics per thread (below, checked at build time against `static-allow.txt`). `surface` lists every engine member reachable from `entries.txt` (what the shim must implement). |
| `Shim/` | `IGTAP.UnityShim`: the Unity API the game touches. Math types (`Vector2`, `Vector3`, `Mathf`, `Color`, ...) are Unity's own managed code (generated by `tools/sanitize-unity.py`, then trimmed by hand to what the game and the engine call: copy a missing member from the script's output, don't regenerate), so float results match bit for bit. `Transform`, `GameObject`, components, `Invoke`, `Physics2D` forward to host backends. |
| `Box2D/` | C# port of Box2D v2 (Unity's classic 2D physics), float math in C++ order, Unity's tunables, exact world `SaveState`/`LoadState` for branching. |
| `Runtime/` | Loads a world export into real game objects (`World`), runs Unity's physics semantics on Box2D (`PhysicsWorld`: fixtures from `Collider2D.GetShapes`, layer/contact masks, raycasts incl. start-in-collider and negative distances, collision/trigger callbacks), steps ticks exactly like `TurboRunner` (`Simulation`), and drives input through the shared `MacroEngine.cs`. `OfflineSolver` is the search itself: worker threads mutate, explore and splice input routes on their own `Simulation`, share the best (course time, then `runTicks`) and hand an archive of explored map cells to the next solve (the plugin's `Solver.cs` only launches `IGTAP.EngineSim.exe solve`). |
| `Cli/` | `IGTAP.EngineSim.exe replay | bench | solve | searchbench | plan | polish | coverage | humanize | map | ultras | fulltas | path | rays | probe | clip | lab`. |

Ground truth comes from the plugin (`EngineSimBridge.cs`):

- `POST /api/enginesim/trace {course, capabilities; routeId | ticks, name, world: true, freshStart}` — a
  turbo run from the solver's start state; writes `<name>.json` (start state + full state after every tick) and
  `<name>.world.json` (every GameObject, collider physics shapes, bodies, script fields, statics, Physics2D settings) to
  `BepInEx/config/IGTAPTasMod/enginesim/`. Unity has no shapes for a collider that is off (an unloaded zone, a disabled
  component), so the export copies each off box, capsule, circle, polygon and edge collider onto a live probe at the same
  pose and writes the probe's shapes: the engine needs them when the game turns the collider on (`ZoneLoader` loading a
  zone at a teleporter). Composites and tilemaps have none while off; an older export has none for any off collider.
  The studio maps draw every zone (`Map.OnObjects`). The header says what a run is scored on (`Simulation.SetTarget`):
  `course` (and `gameCourse`, the game's `courseNumber`, when they differ: Courses 11–15 are Courses 1–5 overgrown), a bonus's
  reward box `finish`, and for a transition `transition: true` (timed in physics ticks, `MacroEngine.PhysicsTicks`)
  with an end box `finish` or `finishStart` (the course whose start gate ends it).
- `POST /api/enginesim/submit {course, capabilities; ticks}` — turbo replay of an offline candidate; saved as the
  category's record route (`<course>_<CAPS> <time>`) when it finishes faster than the current best, or as fast in fewer
  physics ticks from the run start (`runTicks`; the saved route is replayed for its own). On a course it is also saved as
  the farm route (`<course>_<CAPS> farm <runTicks × 0.02>`) when it takes fewer `runTicks` than the farm route
  (`farmSaved`). The reply has both times. Runs are judged from the category's cached start state, but a run that would
  be saved never is from the cache: the cached start is dropped and the reply is a 409 ("loading; retry"), and the retry
  captures the start from a quick restart and judges the run again from it before `SaveSolverRoute` replays it.
  A start is captured only with the player parked at the course's reset point in the course's zone, the zone settled
  (its root and its `ZoneDisableLoadList.toLoad` on: a course's `DisableBits`, its start gate and zip movers) for 10
  frames. Its history is fixed (`CourseStart`, shared with the engine): the Movement fields a quick restart keeps
  (`facingRight` true, `wallJumpFacing` (1, 0), `dashDirection` (0, 0), `wallCoyoteDir` 0, `framesSinceLastDash` 1000,
  `MostRecentUpwardsMoveWasNormalJump` false, afterimage and wall-slide flags, `preDashMomentum`, `finalWallClingTimeLeft`;
  in the air `lastHyperY` 1e8), the RNG and every `clonesScript.timeSinceLastClone` (10000), set after the quick restart
  and again at the capture. Its FloatingOrigin is fixed too: the quick restart puts the world where the game's own
  rebase on the player standing at the start leaves it (each scene root at its loaded position minus the reset point
  12 down, `currentOrigin` minus that point, the player at scene (0, 0); `TurboRunner.PutCanonicalOrigin`). The start
  snapshot's restores put it there exactly again, whatever ran before. The searches (`Solve.Creator`) load a category
  trace's start the same way (`Simulation.LoadStart(start, canonical: true)`: the history, and a trace captured at
  another origin rebased to that one), so a trace captured before this searches from the start the game judges;
  `replay`/`path` load a trace as captured (`path --canonical` as the searches do).
- `POST /api/enginesim/raycast {rays: [[ox, oy, dx, dy, distance, mask]...]}` — Unity raycast probes.
- `POST /api/enginesim/ghost {course, capabilities | fulltas, a, b}` and `POST /api/enginesim/slack {name}` —
  read-only, for the studio's ghost compare and humanize slack: two routes' per-tick positions from the `map` JSON on
  disk (with the first tick their bodies part), and a route's human version's slack report (`<best>-human.slack.json`)
  with its input ticks.
- Full-TAS (`docs/fulltas.md`): `POST /api/enginesim/trace {fulltas: <run>}` writes `fulltas-<run>.json` from the fresh
  new game (a `"start": "vman"` run: the Vman speedrun's world) with the run's goals in the header (`fulltas.goals`);
  `IGTAP.EngineSim fulltas <trace>` searches the whole run in windows of goals and sends complete, faster runs to
  `POST /api/fulltas/submit`. `fulltas <trace> --check <route.json>` only replays a route (a run file's `inputs` or an
  offline best's `ticks`) and prints each goal's physics and input tick, its live time and held frames (dash freezes,
  pauses; a Full-TAS run's time is live time, README `### Rules` 31), and how it ended.

`tools/enginesim-capture.py routes|random|start|route` captures traces; `tools/enginesim-redeploy.py` rebuilds and
reloads the plugin.

## Use

All searching happens here, never in the game (the root `README.md` rules: *Search offline in `enginesim`, never in
the game*). The game is needed once per course/category to capture a start trace and world, and afterwards only to
judge new bests.

```powershell
dotnet build enginesim\Cli\IGTAP.EngineSim.csproj -c Release
$exe = "enginesim\Cli\bin\Release\net10.0\IGTAP.EngineSim.exe"
$traces = "C:\Program Files (x86)\Steam\steamapps\common\IGTAP an Incremental Game That's Also a Platformer\BepInEx\config\IGTAPTasMod\enginesim"
& $exe replay $traces\rand-*.json $traces\route-*.json   # fidelity: first tick where offline != turbo
& $exe bench  $traces\route-c1-none-4.14.json            # single-core speed
& $exe determinism $traces\fulltas-VMAN.json route.json  # a snapshot's runs depend on nothing else (orders, processes)
& $exe solve  $traces\route-c1-none-4.14.json --threads 16 --minutes 60 --stall-minutes 5
& $exe path   $traces\route-c1-none-4.14.json route.json  # where the course timer starts/stops along a route
& $exe humanize $traces\start-c1-none.json $traces\offline-best\1_none-1.66.json  # same-time, easier version + slack report
& $exe probe  $traces\route-c1-wjds-1.06.json probe.json --out result.json  # one start state, branches of inputs, every tick
```

`solve` loads the trace's world and start state on every thread, seeds with the trace's inputs (plus `--seed` traces),
writes each new best to `<traces>\offline-best\`, and sends each best that beats its seeds to the running game's
`/api/enginesim/submit` (skip with `--no-submit`). Each worker walks its best's plateau: a mutation that finishes
exactly as fast (or rejoins the best's state) replaces it (`drifts` in the progress line), since a faster route is often
several mutations away, each alone no faster. A best is the fastest course time; at the same time, the fewest
physics ticks from the run start (`runTicks`), which shortens a flying start's setup before its last start-gate
crossing (off the timer, but a player still sits through it). The search never finishes a run slower on the course
timer than its best, so it doesn't search for farm routes: those come from the judged candidates. With the game closed
the best stays on disk; the plugin judges every waiting `offline-best\` file that beats or ties the saved route (its
category, then the course's other categories), and the group's file with the fewest `runTicks` when that beats the farm
route, as soon as the game is in the world and idle (a studio Optimize run holds the queue only while it starts
each target, and its running target's own files until that `solve` ends), and moves them to `offline-best\judged\`.

Splicing joins explored segments onto the best (`splices` in the progress line). The best's replay records the course
time and input tick of its first arrival in each map cell. An explore run that reaches one of those cells at least a
tick sooner runs on with the best's inputs from that cell (`Splice`). The jump button's press and release flags are
fixed where the two join. Each new best also tries up to 64 archive cells that are already ahead of it, biggest gain
first, including cells from earlier solves. On Course 4 WJ_DS_DJ this took the best from 16.58 to 15.04 within a
minute: the explore archive held faster segments that the whole-route mutations couldn't reach.

A map cell is a 48×48 square (plus the forced-path boxes passed, or a Full-TAS run's goal progress). Ground-tagged
surfaces refill wall jumps, double jumps and air dashes on every touch; `Moss`-tagged ones refill nothing
(`Movement.touchedMossyGround`; the Overworld's `moss` tilemap and the upgrade trees' `Tree*Ground`). While the last
surface touched is moss, the counts left are part of the cell, so an earlier arrival with fewer left doesn't replace,
cut or splice over a later one that has them (`OfflineSolver.CellKey`). A Full-TAS run's cells always keep the counts
left, and its momentum too, in steps of 250 each way on x and y (`MomentumBucket`): a superjump or spike super carries
its momentum for a hundred ticks, so an arrival that has it and one that doesn't don't replace each other.

The guide (`--guide`, experimental and off by default; a `forced-paths.json` rule with `"guide": true` turns it on for
every solve it covers, the studio's too) weighs each explore pick by how close the cell is to the target:
`guide d=` in the progress line is the best cell's walkable distance to it (`--guide-weight W` how hard it pulls, default
1). On two Course 4 WJ_DS_DJ pairs of 2-minute 8-thread arms it won one and lost one (unseeded: 12.62 vs 11.46 lost;
`--rng 4242`: 11.32 vs 11.90 won; the `--rng 777` pair was cut short), so the default stays the plain search. `--rng N`
seeds the search's randomness, worker `i` getting `N + i`, instead of the clock: two runs with the same seed on one thread
find the same bests in the same order.
The distance comes from a Dijkstra field over the static collision geometry on a 24-unit grid of world cells, flooded from
the target (the course's end gate, a bonus's reward box, a transition's finish box or its finish start's gate, or the
current `at:` goal rect in Full-TAS goal mode, which also replaces its straight-line `GoalDistance`; on a course run with
forced-path `via` boxes, the next box the run hasn't passed yet, then the target once it has them all): free where no solid
collider covers a cell's centre, a spike cell six steps. So the number is a heuristic — a mover, a one-way or a coloured
swap is in it only as the world export left it — and the picks keep their pick-count novelty; a wrong number wastes
picks, never a run. The field builds once per world and target, over the region the target and the explored cells cover
(`DistanceField`), and is rebuilt when the static geometry changes (a block swap or a zone load bumps its version).

Tech lives on the ticks where the player's contact changes, and a random burst puts its jump and dash anywhere in its
chunks. So each explore run records its contacts (`ContactLog`), and half the time one of them gets a graft (`tech
grafts` in the progress line): the run is cut around it and a mined tech demo's input window for that contact kind goes
there, then 40 ticks of stick. The Tech tab's demos (below) are the graft library; there are no hand-written grafts. The
contacts, and the demos whose key windows graft there (`techgrafts` ends with this list; `xN` is a pick weight):

The corner hyper contact is seen on every physics step, not only on input ticks, because a dash's ticks consume no input
(`ContactLog.Slide`). It fires when a down-diagonal dash has landed (`canHyper`, flat) and is still dashing with
`onGround` held up by coyote frames only. `corner-boost.graft` presses that dash again a few ticks either way with a late
jump (dash frame 4–12), so the landing moves along the corner and the hyper jumps in coyote time past the edge; its corner
ultra also puts a wavedash 8–16 ticks before it, so the corner hyper carries a hyper's momentum as `preDashMomentum`.

Why corners: a dash lands as soon as a ground ray touches the floor. The rays start 18 below the player and reach 22
further, so past an outer corner (the body beyond the edge, a rear ray still over the floor) nothing stops the body. The
landing can sit up to ~12 u below standing height; a floor stops it at ~7. The hyper that follows can then be under
`lastHyperY − 4`: the game's ultra, which adds `preDashMomentum.x`. Only an offline lab shows this so far (issue #12).

The wall-behind contact is the GC wall clip (the studio's Tech tab): turn toward a wall at your back and the turned
hitbox's front ground ray (x ∓ 25) starts inside it, which grounds you in mid air while `Velocity.y` is under 200.
`wall-clip.graft` flicks the stick toward the wall (0.3–0.55) with the jump released on that tick (a held jump between 150
and 580 up is cut to 50), presses the jump with a light flick back (0.3–1) the next tick, then holds the jump with the
stick at rest for 0–26 ticks. A clip is a ground touch: on a Ground-tagged wall it refills air dashes, double jumps and
wall jumps.

Clips come in chains, and the states between them don't survive as cells: a square keeps its earliest arrival, which is
seldom the slow one that stopped with a wall at its back. So a clip graft's run records its own contacts, and the next
wall behind after it gets the next clip, up to four deep, with the stick drifting left, right or at rest after each hold
(the demo's `chain`, `expect`ing the clip's landing). A clip-ready state (a wall behind, as above) is also its own cell
(key bits 45–46 in a course), and an explore that starts in one counts the wall behind as a contact on its first tick.

The wall-ahead contact sets a clip up: the stick turns away from the wall for 1–4 ticks (0.3–1) and rests for 3–30, so
the player drifts to a stop with the wall at its back (under an overhang's corner, as Course 1 NONE does at the pillar's
left face); the chain then clips off it. A wall above the back gets the same rest with no turn, so the player rises up to
it clip-ready.

The start-gate contact is the late gate touch (Tech tab): the timer starts on the first tick the player overlaps the
start gate, so a route can reach the far side of it untimed and brush it at the last moment. Its demos rest from the
contact for 0–20 ticks (the `.jump` demo presses the jump at the contact, for a player standing by the gate), tap toward
the gate for 1–2 ticks (0.3–1) and back for 1–2, then rest with the jump as it was; one contact tries 8 of these, each
chaining clips. The progress line counts `tech grafts`, `chained` and `expected contacts` (chain grafts whose run showed
the demo's contact after it: a clip that landed), and `at step contacts` (grafts at a per-step kind).

The graft library is the Tech tab's demos (techs.json), mined into graft patterns
(`Runtime\TechGrafts.cs`). Each demo replays offline from its start (its category's start trace, its own savestate, a
captured `tech-<id>.json` trace, or a lab map's solved `labmaps\<id>.demo.json` over the trace it was solved in), the
contacts along it are detected with the same detection as above (the shared
`ContactLog`), and the input window around its contacts (10 ticks before to 30 after: stick values, presses/holds/releases,
dash, dash jump, dash turn (`turnX`/`turnY`) and pause) becomes a pattern tagged by contact type and the unlocks it needs (its
`requires` and omnidash; for a lab demo the demo file's `requires`, else the tech's narrowed to the unlocks both it and the
lab's `category` hold; a window that presses dash needs the dash, one the demo double jumps in the double jump). The window
nearest the demo's last press, release or dash is its key
pattern (a tech's `graftKey` in techs.json, `{"contact": "<Contact>", "tick": <demo input tick>}`, centres it on that
contact instead, for a demo with trailing inputs); up to 8 contacts make patterns, and each side-tagged one is also offered
mirrored for the other side. A window with no button in it is travel and is dropped, except at a contact the player ran into
(a spring, a spike, an overhang or slope, a step-up), where the stick that meets it is the tech.
A tech with a lab demo that resolves (its `labmap`/`labDemo`, the repo's, or a lab map whose `tech` names it) is mined from
its lab demos alone; its captured `tech-<id>.json` trace or demo macro (recorded from a course start, with the travel and
noise around the tech) is mined only when it has none. Besides its studio default, a tech mines its lab's `graftDemos`
(techs.json: `["from-floor"]` mines `labmaps\<labmap>.from-floor.demo.json`; never the comparison ghosts, which fail on
purpose), and every lab variant demo (`labmaps\<lab>.<name>.demo.json`) that carries a graft spec, for the tech the demo
file names (`"tech"`) or else its lab's. A tech marked `"graft": "todo"` (not demonstrable yet: no lab) mines nothing, and
the listing says `todo` instead of counting it missing. A window with a quick restart is mined too, flagged: only a run
that may restart (a Full-TAS window with resets allowed; the game's `RestartRefused` still
aborts a refused one) grafts it, never a course solve, `plan` or `coverage`.

A lab demo's graft spec (`"grafts": [...]` in the demo file; `TechGrafts.GraftSpec`) replaces that demo's automatic windows
with exactly the ones it names, each a key window: `contact` (+ `tick`: the demo's contact of that kind nearest the tick),
`window` `[first, last]` around it, `as` `[{"kind", "shift", "weight"}]` (the contact kinds it grafts at, default its own),
`shift` `[lo, hi]` (where the window's contact lands relative to the run's; default ±3), `vary` (runs of equal ticks
sampled at graft time: `{"at": offset, "ticks": length choices, "x": stick magnitudes, "stick": [x, y] pairs, "dashJump":
frames, "button": "run"}`; a choice list or an `"a..b"` integer range; `"button": "run"` keeps the grafted run's own hold,
no new edge), `coast` `{"x": choices, "held"}` (the 40 coast ticks after it), `dir` (the way the run was going for a window
whose stick is against it: a backwards dash), `tries` (grafts per contact, each sampled anew), `weight` (how often a pick
draws it: a tech is drawn by its largest weight at that kind) and `chain` `{"depth", "on": kinds, "with": tech, "expect":
kind, "shift"}` (the graft's run records its contacts; the first contact of an `on` kind 2+ ticks after the placement gets
a key window of `with` placed `shift` after it, up to `depth` deep, 85% of the time, and with `expect` only when the run
shows that contact where the demo did: the clip grounded the player). A window at a contact with no side is turned to the
run's direction (its last stick before the placement), the other way 30% of the time; a stick choice is relative to the
window's direction. `techgrafts --contacts` lists each demo's contacts; the listing shows each spec'd pattern's spread and
ends with the techs per contact kind.

The spec'd demos that carry the old hand-written grafts' spread (labmaps, all hand-built and checked by `lab replay`):
`wall-clip.graft` (the clip at `WallBehind*`: flick 0.3–0.55, flick back 0.3–1, hold 0–26, 0–24 after the contact, chain 4
deep expecting its `Landed`; the rest at `WallAbove*`, 3–30 ticks; the turn away at `WallAhead*`, 1–4 ticks 0.3–1 then
3–30 at rest, each chaining clips), `late-gate-touch` (new lab by Course 1's start gate; its default and `.jump` demos: rest
0–20, tap 1–2 ticks 0.3–1, back 1–2, rest 5–30, 8 tries, chaining clips), `coyote-ledge.graft` (the jump at a ledge −4..+3,
hold 1–40), `landing-tick-jump.graft` (the buffered jump −4..+1 of a landing), `wall-coyote-window.graft` (the wall jump:
0..+4 after leaving a wall, −3..+3 of a touch), `spike-grace.graft` (the jump 1–7 ticks before a death), `coyote-ledge.super`
(tech `super`: the dash with its jump on frame 1–4, or none, at a ledge, landing, wall or death), `coyote-ledge.primed`
(`super`: the jump held into a dash 1–6 ticks later), `backwards-dash-jump.graft`, `superbounce-wall.graft`, and for the
omnidash `wavedash`, `ultra`, `dash-bounce`, `wave-bounce`, `high-super` (the wavejump), `wall-dash` (the eight aims),
`freeze-aim` and `corner-boost` (the corner hyper, frame 4–12, and the corner ultra) `.graft` demos.

The hand-written grafts are gone: every contact is grafted from these mined windows. Two tuning switches remain:
`--no-graft-specs` (drop the spec'd windows) and `--mined-draws N` (mined windows per grafted contact, default 1). The
progress line counts `tech grafts`, `chained` and `expected contacts` (chain grafts whose run showed the demo's contact
after it).

Besides the tick contacts above, `ContactLog.Step` files per physics step (a dash's steps consume no input tick, and a
spring or a spike acts inside a physics callback) the contacts the game's own calls and the player's touches make, at the
input tick that step belongs to: `SpringHitLeft`/`Right` (a spring whose up has an x, named by the side it launches toward)
and `SpringHitUp`/`Down` (`Movement.hitSpring`), `DoubleJump` (an air jump spent), `DashJump` (a super or hyper out of a
dash, or a ground bounce's jump), `WallBoostLeft`/`Right` (`Movement.SpecialWallJump`: a wallbounce, a dash into a wall with
the jump buffered, a dash-boosted wall jump; the wall's side), `Landed` for a landing the same tick jumps out of (the ground
rays touched ground, onGround already off again), `Paused` (a route's pause), `SteppedUpLeft`/`Right` (a step-up after a step
without one), `SpikeTouched`/`SpikeCleared` (a spikeScript trigger touched, or left alive), and `OverhangLeft`/`Right` and
`SlopeLeft`/`Right` (a solid surface newly touched whose normal is neither axis-aligned, facing down or up; the surface's side).
They come from observer hooks the retarget adds (`hooks.txt`: `hitSpring`, `SpecialWallJump`, `StepUpAnimationScript.onSteppedUp`,
and the existing `playSFX`/`touchedSolidGround`) into `Simulation.Events`, and from the player's touching pairs after each
step (`PhysicsWorld.PlayerTouch`); a run's first step only primes the touches (a spike it starts in isn't a touch). The solver
records them on every explore step and grafts the mined windows there with the same jitter and unlock filter; a contact is
drawn only among the kinds the mined windows offer at the run's unlocks. `plan` makes them nodes when a mined window grafts
at one of their kinds, and `coverage` records
them too.

`IGTAP.EngineSim techgrafts <traces dir>` lists the patterns per tech. A `solve` grafts them at their contact kinds,
jittered ±3 ticks (or as the graft spec shifts them) and filtered by the run's category unlocks (`tech grafts` in the
progress line): a graft draws a tech first (so a demo with many contacts doesn't crowd out a short one), then its key window
60% of the time, and a new best it finds says so (`via tech graft <id>`). `--no-tech-grafts` turns grafting off.
Whatever trace is solved, the demo traces, savestates and the cache resolve from the configured traces dir
(`tools/gamepaths.py`'s TRACES: the game's config folder's `enginesim`, when it exists), so a copied trace mines or reads the
same patterns as the real folder; `--tech-dir <dir>` overrides it. The catalog is the plugin's merge (`TechCatalog.MergeSeedTechs`)
done on every load, so a tech or demo added to the repo mines before the game has run: the config folder's `techs.json`
keeps its own entries, and the repo's `techs.json` adds the techs it lacks (not one the Tech tab deleted: listed in
`techs.seeded.json`). The repo is the source of truth for the demo wiring: a repo entry's `labmap`/`labDemo` and `graftKey`
replace a live entry's (a live `labmap` that differs is mined too), and the live ones fill in only where the repo has none.
The repo is the source tree the engine was built from (walked up from the binary, else the path the build recorded:
`IgtapRepo` in `IGTAP.EngineSim.Runtime.csproj`, for a solver copied out of the tree; else the copies beside the binary).
Lab maps resolve from the repo's `labmaps\` first, then the config folder's (the studio's copies fill in only the labs the
repo lacks: a copy there goes stale when the repo's lab is edited), then the build's; a lab map whose `tech` names a tech is
mined for it with its default demo. The mining is cached in
`<traces>\tech-grafts.cache.json`, keyed by what the miner reads (each tech's demo fields, where its demo resolved, its demo
macro, the files it replays over), the miner's version and the engine build, so a note edit or a newly saved route doesn't
re-mine (`techgrafts --refresh` re-mines); a grafted window keeps real button edges at the cut (a press or release as a
controller makes them).

Before the timer, a course cell also keeps where the player is going (`OfflineSolver.Motion`, key bits 47–49: vertical
speed below −200, under 200, under 580 or above, and the facing). An untimed set-up is slow on purpose, and without
these bits every state of it lost its square to an earlier arrival going the other way.

A solve picks up where the last solve of the same target stopped. Its search state goes to `<traces>\archive\<label>.json`
(`<course>_<caps>`) every minute and when it ends, so a solve the studio stops (it kills the process) loses at most the
last minute. The file holds every explore cell's input prefix with how
often it was picked, plus the plateau (each worker's route as fast as the best, drifted away from the saved one), and
a running count of all runs. The next solve replays the prefixes, split across its workers, to rebuild the cells
(~700k ticks for Course 4 after one session, a few seconds). Well-explored cells keep their picks, so exploration
goes on from the frontier and doesn't start again from the course start. Each worker also starts drifting from a
plateau route instead of the saved route. A plateau route's result is not submitted: its file was written when it
was found. `--fresh` ignores the file for this solve but still overwrites it.

Coordinates: three frames, three types (`Runtime\Frames.cs`), so mixing frames is a compile error. `WorldPos` is the
game world's frame: the scene position minus the game's `FloatingOrigin.currentOrigin`; every position you give or read
(forced-path boxes, `--via`/`--avoid`, the studio map's readout, `path`'s `pos`, `courses.json`, `at:x,y,w,h` goals) is
in it. The game shifts every root object whenever the player strays `Threshold` (17500 in every Overworld export) from
the scene origin, so a capture's scene frame depends on where the game was when it was taken (Course 1's start gate:
scene x -241 in one capture, 2000 in another); the world frame doesn't. `ScenePos` is the scene frame now (transform
positions and raycasts; `ScenePos.From` and `AsVector2` are the only raw-vector escapes, at those Unity API boundaries).
`CapturePos` is the scene frame at the trace's capture. A simulation keeps its capture's origin (`Simulation.Origin`,
the frame of the trace's rects, goals and map cells) and its current one (`Simulation.CurrentOrigin`), converts between
the frames around them (`sim.ToScene`, `sim.ToWorld`, `sim.ToCapture`, `sim.FromCapture`), and reads the player's
position per frame (`Simulation.PlayerWorld`, `Simulation.PlayerAtCapture`); a box is checked against the frame it is
given in. Only the trace files themselves
(samples, the world export, the header's goal rects) stay in their capture's scene frame; each sample carries the
`origin` it was taken at.

Turbo, 1x and the engine all rebase. At 1x `FloatingOrigin.LateUpdate` sees the player past `Threshold` after a
tick's `Update` and starts `MoveOrigin`, which waits for the next physics step (`WaitForFixedUpdate`) and then moves every
root object of the active scene back by the player's scene position and lowers `currentOrigin` by it. It leaves the
scene-frame numbers the game keeps (`lastHyperY`, `courseResetPoint`) alone: that is the Float Ultra (a chained hyper
whose second jump is ~11,700 u under `lastHyperY` after a rebase). Turbo runs the game's own `LateUpdate` after each
tick's `Update` and resumes the coroutine right after the next `Physics2D.Simulate` (`TurboRunner.OriginFrame`,
`ResumeRebase`); a turbo snapshot carries `currentOrigin` and a waiting rebase, and a restore moves the world back to
it (`TurboRunner.PutOrigin`), so every judged run starts where its start was taken (before this, turbo never rebased
while 1x did — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Turbo never rebased*).

The engine does the same (`Simulation.FloatingOriginFrame`, `ResumeRebase`, `MoveWorld`): every transform of the active
scene moves back by the reference (a root's local position with it), `currentOrigin` drops, bodies take their
transforms and body-less colliders rebuild their shapes at the next sync, as Unity's do. A body-less box or capsule is
rebuilt from its own geometry and the moved transform in float math (`PhysicsWorld.MovedShapes`); 590 of 591 boxes and
all 85 capsules match Unity's shapes in a VMAN world exported after a rebase (a child transform moves by the reference
too, which matches Unity's own position for ~90% of children; the rest are an ulp off). A snapshot keeps the list of
rebases, and a restore across one rebuilds the world from the capture's poses (`MaterializeRebases`). Past a rebase the
VMAN run's trace (rebase at tick 1168) and the Float Ultra demo's (three rebases, the ultra at tick 1206 with 2740
momentum) replay with every position and Movement field identical; only the body velocity differs on a few landing ticks
(under 3e-5, the ground-seam noise below). `ultras` models the rebase itself on its placed launches (`Rebases` off
there).

After a rebase the tick's rendered frames end with the player at the step's end moved with the world (`_stepTo`, as
turbo's `Place(player, _stepTo)`), not at the Box2D body, which only follows at the next sync (reading the body there
let a far teleport rebase every tick or two — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Far teleport rebased
every other tick*).

The game's mutable statics (`Singleton<T>.instance`, `VmanScript`'s flags, `globalStats`' dictionaries) are
`[ThreadStatic]` in the engine's copy of the game (`Prep`'s `ThreadStaticFields`), and a thread's `World.Load` sets its
own world's; a `Simulation` runs on the thread that loaded its world, as the shim's backends already required (they
used to be shared by every solver thread — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Statics shared between
solver threads*). The visits map is versioned (`VisitsVersion` 2).

A build-time check (`Prep`'s `StaticAudit`) keeps the split from silently rotting: every static field the rewritten game
writes outside a static constructor, or whose contents it mutates (the shim's own mutable statics too), must be per
thread or listed in `enginesim/static-allow.txt` as `Type::field  # reason`, else `retarget` fails the build listing the
offenders (removing one field's per-thread treatment names it). A listed field stays shared between solver threads, so
each reason says why the world exports agree on its value (every claim checked against the corpus's 225 `*.world.json`)
or why no run reads it: the cash/upgrade localisation tables and the symbol, difficulty and clone-fade settings, the
trip breaker's lambda caches, the shim's layer database and instance-id counter, and the `Physics2D`, `Camera.main` and
`Time` fields nothing writes. `Time.fixedDeltaTime` and `Time.timeScale` (written per world load and by `Movement.Start`)
are `[ThreadStatic]` in the shim itself. Re-check the list on a rebase: a new export that disagrees with an entry breaks
the sharing assumption the entry documents.

### Course --auto

```powershell
& $exe solve $traces\route-c4-wjdsdj-13.28.json --auto --threads 4 --minutes 5 --window-minutes 0.25   # --farm, --seed FILE, --parts LIST, --focus a-b, --waypoints-out FILE, --fresh, --log-json FILE
```

`--auto` (`Cli\CourseAuto.cs`) runs the Full-TAS `--auto` loop ([`docs/fulltas.md`](../docs/fulltas.md#auto), its parts
included) on a course. The course becomes a Full-TAS run: its goals are waypoints along the best's path
(`CourseWaypoints.For`: area goals, the course's checkpoints and springs, forced-path `via` boxes; in record timing the
start-gate crossing `start:<course>`) and the finish (`finish:<course>`; a bonus's reward rect, a transition's next
`start:`). Waypoints are checkpoints, not cut points: every window plays on from the state the route has there, so
momentum carries through them, and a window is scored on its arrival.

- **Timing.** Record (the default on a gated course): the game timer, the finish's tick less the start-gate goal's
  (`FullTas.TimerGoal`; `Route.Last` compares that, `Route.End` is the finish's tick from the quick restart). A window is
  scored on its arrival's physics tick, which is the timer's only once the gate crossing is in its prefix, so in record
  timing the loop's windows start after the gate (`--focus` defaults to the goals after `start:`; combine still splices
  the run-up). `--farm`: physics ticks from the quick restart to the finish. A bonus or transition is timed from its
  start either way.
- **Rules.** The course and category's `forced-paths.json` rules (with `--optional`/`--no-optional`) are every window's
  and every polish's avoid boxes; the start's player must have the category's unlocks (the trace's `capabilities`),
  else it stops.
- **Start.** The fastest finishing route (on the timing) of the trace's own, each `--seed` and the last `--auto` best;
  the others are the loop's `--ref` routes (combine splices their goal runs in).
- **Files.** The run lives in `<traces>\course-auto\` (`fulltas-<run>.json` and its world, `fulltas\<run>.json`, the
  archive, `.auto.jsonl`, `.auto-refs.json`), the run named `course<N>_<caps>[-opt-...][-farm]`. Every kept best is played
  again on the plain course simulation and written to `offline-best\<course>_<caps>-<time>.json` as `solve` writes it
  (the game timer's time, `runTicks`), so the plugin judges it for the record and the farm as any solve's; the log line
  is solve's `offline best X.XXs via auto: ...`, and `course check: DISAGREES` flags a timing the course simulation
  doesn't confirm.
- **Waypoints.** `waypoints {json}` on stdout at every kept best (goals, rects, splits, `timerGoal`, record and farm
  ticks); `--waypoints-out FILE` writes it and exits without searching (the studio's list). `--focus a-b` numbers goals
  in that list.
- **Studio.** The Optimize tab's **Improve** runs this (`Solver.cs` `CourseSolveArgs`): the Improve a course panel
  improves one target, record or farm (**Timing**), and the Improve many matrix queues ticked record and farm times.
  Clicking a time opens that target: the panel lists its waypoints (`POST /api/solver/waypoints {course,
  capabilities, optional?, farm?}`, the engine's `--waypoints-out` on the library's routes; live from `waypoints {json}`
  while that target improves) with each one's split, and **Show map** draws them numbered. Click a waypoint
  (shift-click extends) and Improve sends `focus: [a, b]` (`--focus a-b`). A target without a category route of its
  category or a narrower one runs the plain `solve` first (**Solve**); so does an Improve whose routes all come from a
  narrower category and none finishes this one (an added `OM` or `ORB` changes what the same inputs do: Course 10's
  `WJ_DS_DJ_BS_ZIP` route dies in `WJ_DS_DJ_BS_ORB_ZIP_OM`). The plugin launches `solve <start> --seed
  <each library route of the course> [--optional/--no-optional] --threads <cores - 4> --minutes M --auto [--farm]
  [--focus a-b]`; `POST /api/solver/preview` (the start body) returns each job's command without starting anything.
  Below the counts, the panel's "Should it keep going?" card shows the engine's last `outlook`: the verdict, what to do,
  the chance of a gain per hour and within the run's remaining minutes, the median wait, what the odds rest on (the
  folder's other Improve runs and their gains past a dry spell this long), the search spent on this target across every
  Improve, the room to the floor, and the pulls running now with how often such pulls gained before (`outlook` and
  `pullStart`, [`docs/fulltas.md`](../docs/fulltas.md)).
  The raw engine log is folded under it.

## Search bench

Search changes are judged on a suite, over several seeds, not on one run: a single `solve` is mostly seed noise (issue
#18). A search change stays on by default only if its median beats the current solver's on the suite.

```powershell
& $exe solve $traces\start-c4-wjdsdj.json --no-submit --fresh --rng 1 --log-json bests.jsonl
& $exe searchbench enginesim\Cli\searchbench-suite.json --seeds 5 --minutes 2 --threads 8 --arms '{"base": [], "guide": ["--guide"]}'
```

- `solve --log-json <file>` writes one JSON line per new best: `wall` (seconds since the search started), `time`,
  `runTicks`, `ticks` (physics ticks simulated so far, all threads) and `how`. `--no-humanize` skips the background
  humanize (the bench passes it, so humanize doesn't take CPU from the search); `--tech-cache <file>` puts the tech
  grafts' mining cache there instead of the traces dir.
- `searchbench <suite.json> [--seeds N] [--minutes M] [--threads T] [--arms {name: [solve args]}] [--traces dir]
  [--out file] [--keep]` runs `solve <copy> --rng s --no-submit --fresh --no-humanize` for every suite course, arm and
  seed `s` = 1..N, one after the other (the arms take turns seed by seed, so a load that comes and goes falls on each alike), each as a child process on its own temp copy of the start trace and world
  (`%TEMP%\igtap-searchbench-<time>\<course>\<arm>\seed<s>`), so its `archive\`, `offline-best\` and everything else it
  writes stay there. The bench copies the traces dir's `tech-grafts.cache.json` once into its own folder and every run
  uses that copy (a build change re-mines it there), so nothing is written to the traces dir. `--arms` is JSON or a
  file holding it (default `{"default": []}`); a suite course's `args` go before the arm's. An arm's `--exe <path>` runs
  that build's `solve` instead of this one (with its own cache copy), so two builds bench on the same seeds, interleaved
  (`{"old": ["--exe", "old\\IGTAP.EngineSim.exe"], "new": []}`). It prints and writes
  (`--out`, default `searchbench.json` in the bench folder) per course and arm the median, min and max over the seeds
  of: wall seconds to the first finish, wall seconds to the course's `target` time (at or under), and the final best;
  a run that never got there counts as never (`-`, above every number), so a `-` median means half the runs or more
  missed it. Each run's best lines are in the output too. The run folders are deleted unless `--keep`.

## Probe

`probe <trace.json> <probe.json> [--out file]` tests exact inputs from one state and logs every physics tick of each
branch: position (world frame), `Velocity`, `momentum`, body velocity, ground/wall, cutscene mode, dash state and
direction, facing, plus any Movement fields listed in `fields`.

```json
{
  "start": { "savestate": "C:/.../savestates/<id>.json", "position": [3028.1, -245], "velocity": [0, 0], "scaleX": 1,
             "fields": { "facingRight": true, "airDashesLeft": 1 } },
  "prefix": [ { "x": 1, "held": false, "press": false, "release": false, "dash": false, "dashJump": 0 } ],
  "branches": [ { "name": "dash+jump", "ticks": [ ... ] } ],
  "extraTicks": 30, "fields": [ "wallJumpsLeft" ]
}
```

Every key is optional. `start` changes the trace's start state before the run: a studio savestate (its world position
is its scene position minus the FloatingOrigin it recorded, so savestates captured before the plugin recorded it are
refused), then a world-frame `position`/`velocity`, `scaleX` and Movement fields by name. Every branch runs `prefix`
then its own ticks; with no branches the prefix runs alone.

Every run models 1x with the player body's interpolation on, on playback's fixed clock (`MacroEngine.FrameGrid` at
`MacroEngine.PlaybackFrameRate`, as turbo does): before each `FixedUpdate` the transform holds the last frame's blend
of the body's last two positions (`Simulation.LagForFixedUpdate`), and after the step every frame between two ticks
runs `Movement.Update` at its blend, a dash freeze's frames first (`InterpolatedFrames`; `hooks.txt` reports the
`TimeStop` call, whose body stays cut). A step-up in any frame moves the body there. Checked against the plugin's 1x
probe: Test-No-Omni-Skip's 7.92 inputs at 280 fps (90 ticks, within 0.001, both dying at action 14) and a Course 1
route at 240 fps (a dash freeze of 12 frames and a step-up, tick for tick).

The in-game counterpart is the plugin's 1x probe (`ProbeRunner.cs`): `POST /api/probe/run {name, route: "1_WJ_DS",
savestateId?, ticks, captureAt?, fps?, omniDash?, pauseAt?, pauseOffset?, pauseFrames?}` plays the ticks at normal speed from the category's quick restart
(a Full-TAS run's `route: "fulltas/VMAN_NONE"`: from a new game of that run; or the savestate); `tech: <id>` plays that
tech's demo as its playback does (its start, inputs, savestate or lab map, unless `route`/`ticks`/`savestateId` are given;
`tools/probe.py <name> --tech <id>`), and writes
`BepInEx/config/IGTAPTasMod/probes/<name>.json`: one row per physics tick (`kind: "tick"`) and one per rendered frame
(`kind: "frame"`, with `timeScale`, so a TimeStop's frames show as `timeScale` 0). Positions are in the world frame; each
row also has the FloatingOrigin (`originX/Y`), `lastHyperY` (scene frame: world y + `originY`), the game time (`time`),
the camera (`camX/Y` in the world frame, `camSize`) and Cash (`cash`). `captureAt`
saves a studio savestate (`probe/<name> @<tick>`, with its FloatingOrigin) after that input tick, the start for later
probes there. `pauseAt` opens the pause menu (`pauseMenuScript.menuButtonPressed`, what the Pause button calls) right
after that physics tick, or `pauseOffset` `Movement.Update` frames after it, and `pauseFrames` closes it after that many
frames (rows have `paused`): `timeScale` is 0 and no FixedUpdate runs, but Update's step-up runs every frame
(`tools/probe.py --pause-at --pause-offset --pause-frames`).
A probe's ticks can also carry a route's own pause (`pause`, `pauseTick`, `pauseFrame`: `MacroStep.pauseFrames`), which turbo
and enginesim model too (`MacroEngine.FrameRepeats`, `Simulation.InterpolatedFrames`); `pauseAt`/`pauseOffset` are 1x only. Offline
`probe` takes `base` (inputs played once, unlogged, as every branch's start) and `frames: true` (a row per rendered frame:
`kind` `frame`, its `alpha`, `still` in a freeze or pause). Playback runs on a fixed clock at 280 fps with
vsync off (`TasPlugin.PacePlayback`); `fps` sets that rate instead (turbo and enginesim model 280). Keep
it at 50 or more: playback runs at most one physics tick per frame (`Time.maximumDeltaTime`), so below 50 the game slows
down. `GET /api/probe/status` says whether one is running and the last file written. `fields` (Movement field names)
adds those fields to every row, as `probe`'s `fields` do; every row also lists the zip movers within 300 u (`movers`: world
position and `layer`, 7 Ground, 0 while `MakeIntangible` holds it).

A probe of a route also logs the RNG's consumers, to find where 1x and the engine split on Cash: a `clone` row for every
`clonesScript.SpawnClone` (course, instance id, on screen, the offscreen divisor before, `nextDue` after, Cash before
and after, the RNG state before, and the clonesScripts whose `Update` ran earlier in that frame), and an `rng` row for
every call of a game method that drew (`Audio.PlayAudio*`, `Movement.playSFX`, the `Start` of lights, animators and
refill orbs, `ObjectBobber.OnEnable`, `upgradeBox.OnEnable`, `courseScript.Start`) with the object's name and the state
after. Their offline counterpart is `fulltas <trace> --check <route> --ticks-out FILE`: a JSON line per physics tick
(position, velocity, Cash, each course's reward, reward tier and comp boost, the RNG state), per clone spawn (course, on
screen, divisor, fastness and bigness rolled, payout) and per draw (the engine method that drew). Compare Cash as the
sequence of values each side takes, not tick by tick: 1x's physics count runs ahead through dash freezes.

Every position write in `Movement.FixedUpdate` (a jump's `+2`/`+5`, a wall jump's `+1`, the dash's `−20`) starts from
the transform, which holds the last rendered frame's blend of the body's last two positions, so each one pulls the
body back by that frame's lag. On the wall clock the lag changes from run to run, and so does the route; playback's
fixed clock pins it: every frame's game time is a step on a grid half a frame off the physics tick
(`TasPlugin.FixedClockStep`, `Time.captureDeltaTime`). Three scripts read the wall clock, which `captureDeltaTime`
leaves alone (`TasPlugin.PatchWallClock`); during playback they read the fixed clock's frame and its running total
instead: `Movement.TimeStop`'s freeze (so a freeze always runs the same number of `Update` frames),
`cameraMover.LateUpdate` and
`ObjectBobber`. A playback starts with the camera settled on the player (`SavestateService.SnapCamera`). `timer`'s
play-time display still counts the wall clock.

A write from a physics callback inside the step moves the body at once and drops the interpolation: a sideways spring
(`SpringScript.OnTriggerStay2D` → `Movement.hitSpring`, `transform.position += up * 10f`). Turbo syncs it right after
`Physics2D.Simulate` when the transform has moved off the body (`TurboRunner`), and the engine does the same when the
player's transform is dirty after `Physics.Simulate` (`Simulation.Run`) (before this both dropped the push, and a
sideways spring came out 10 u short of 1x — [`docs/fidelity-log.md`](../docs/fidelity-log.md), *Sideways spring lost
its push*).

`POST /api/savestates/place {name?, from?, x?, y?, vx?, vy?, facing?, fields?}` makes a probe start anywhere, inside a
wall too: a copy of a studio savestate (`from`) or of the player now, with the world-frame position, `Velocity` (the body
gets `Velocity + momentum`), facing (±1) and any Movement fields (`{"OnWall": true, "wallCoyoteFrames": 7}`) replaced. It
is saved as `lab/<name>` and returns its `id` for `savestateId`. A lab start is for experiments, never a route's.

## Clip lab

`clip` runs states no input has reached yet: the player anywhere (inside a wall too), at any speed, with any Movement
fields, against many input branches at once, on every core.

```powershell
& $exe clip map $trace 2400 -120 2560 320 4              # ground ('#', layer 128) and spike edges ('S', layer 64) in the world frame
& $exe clip run $trace lab.json --out runs.csv --top 20   # every start x every branch, ranked by the height reached
& $exe clip log $trace lab.json 0 "turn jump"            # one start x branch, tick by tick (the probe's fields + wallJumpFacing)
& $exe clip log $trace lab.json 0 "turn jump" --fields lastHyperY,canHyper,coyoteFrames   # plus any Movement fields
```

```json
{
  "base": { "x": 2543.5, "facing": 1, "onGround": false, "OnWall": false, "collider": "dash", "airDashesLeft": 1 },
  "axes": { "y": [-90, -60, -30], "vy": [-300, -900] },
  "prefix": [ ],
  "branches": [ { "name": "turn jump", "ticks": ["0,-1,DT-1", "0,-1,P", "0,-1,H*8"] } ],
  "horizon": 40
}
```

Starts are `base` crossed with every `axes` value, plus an explicit `starts` list (each on top of `base`). A start's keys:
`x`, `y` (world frame), `vx`, `vy` (the script's `Velocity`; the body gets `Velocity + momentum`), `mx`, `my`
(`momentum`), `facing` (±1: `localScale.x` and `facingRight`), `scaleX`, `collider` (`default` | `dash`: the box's size
and offset), `savestate` (a studio savestate first), and any other Movement field by name. A start with no keys is the
trace's own start, untouched, and the inputs begin on the first tick (no wait for three grounded ticks). `prefix` runs
once per start (`Simulation.Advance`) and every branch restores the state at its end, so a legal approach can go in
`prefix` and the lab still runs thousands of branches from its end. A tick is the probe's object or a string
`"x,y,flags[*n]"`: `H` held, `P` press (held), `R` release, `D` dash, `Jn` dashJump n, `Lx:y` the stick through the
dash lock, `Tx` or `Tx:y` the dash turn's stick (below); `*n` repeats it. `run`
prints the best runs by height and writes one CSV row per run (start keys, branch, `maxY` and its tick, `endY`, x range,
the highest `Velocity.y + momentum.y` and `Velocity.x + momentum.x` on that tick, the highest body velocity up, the fastest body velocity sideways, end reason).

`labs/c1-hanging-wall.json` is issue #10's lab: starts along and inside Course 1's hanging wall (right face x 2528, bottom
y −87) against dashes with and without a turn, with and without a jump. `labs/c1-air-turn-climb.json` is the climb's
air entry: starts facing away from Course 1's wall at x 3488, 2.5-36.5 u from it, a turned dash against a dash pressed

## Lab maps

`labmaps/<id>.json` is a lab map: a custom level piece injected additively into a world's empty space to demonstrate one tech
exactly — a coyote jump off a plain ledge where no course has a clean one. Shapes (box, polygon, edge) sit relative to an
anchor in the world frame, with a Unity layer and tag (`Ground` refills jumps and dashes on touch, `Moss` refills nothing,
`"spike": true` adds the game's `spikeScript`, `"spring": {upForce, strength, movementLock}` on a trigger adds the game's
`SpringScript` with those serialized fields, no Animator, and a box's `rotation` (degrees about z) turns its collider
and its `transform.up`, a spring's launch: 180 points it down), then the player's start (position, velocity, facing,
Movement fields), a finish box, `category` (the unlocks its demo runs with) and `tech`/`techNote` (the tech it
demonstrates). The game (`LabMapService`) and the engine (`LabMap.Inject`) build the same float rotation, and a world
captured with the lab in it exports the spring like a scene one (`Map.cs` reads its launch from the object's rotation).
The repo's `labmaps/` seeds the config folder's like techs.json.

- `lab space <trace | trace.world.json> [w h] [--route <trace>]... [--list N] [--lab <labmap.json>] [--index N]` lists the
  empty rectangles at least `w x h` in the world frame: no collider, trigger or zone geometry at all (the world export, off
  colliders and every zone's included, so the region is the same whatever is loaded), ranked by distance from the routes'
  paths. `--lab` records the best one (or `--index N`) as the lab map's `anchor` and `region`.
- `lab solve <trace> <labmap.json> [--max-ticks N] [--threads N] [--out <file>] [--exact] [--forbid-jump-not-grounded]
  [--forbid-wall-coyote-jump] [--forbid-boosted-double-jump] [--from <demo.json> [--from-inputs N]]` injects
  the lab into the trace's world (static colliders on the ground body, correct layer and tag, before the `Simulation` is built),
  puts the player at the lab start (inside its first tick, as the in-game demo starts: the plugin starts the engine in
  `Movement.FixedUpdate`'s prefix after `MacroEngine.BeforeTick` ran idle, so that tick's pre-hook stick read is at rest
  and the first step is pressed at the input hook, `Simulation.StartsInsideTick`; before this a first tick holding the stick
  down slid a cling faster offline than in the game, and the stored superbounce demo's landing came a tick early offline)
  and searches for the minimum-tick human-legal input sequence to the finish box: exhaustive
  breadth-first over the input alphabet (stick x −1/−0.55/0/0.55/1, y −1/0/1, the jump button's press/hold/release by its state,
  a dash with any dash-jump frame 0–12; a dash press is pruned when the run can never dash) and bounded by the first finish —
  every state below the bound is explored to prove the bound is the minimum. Three admissible prunes cut provably dead states
  (each allows for the player's collider, since the finish is a touch of the box by it). The free-flight bound
  (`LabFlight.cs`): a state whose dash is spent (`airDashesLeft` 0, and only a contact refills it), off ground and wall
  (`cutsceneMode` none, `wallCoyoteFrames` 0 or less, no final cling), gets the highest its transform can be on each tick up
  to `--max-ticks`, from `Movement`'s own constants: `Velocity.y` falls at least `gravity` a tick (at most 1.4 x
  `fastFallMod` of it), gains the apex anti-gravity only under 200, and only the double jump raises it (745 + half a
  `Velocity.y` under 200 with the boost control, under 700 without; a fork per tick it can happen), the jump cut only lowers
  it, `momentum` only decays, and `Velocity.x` stays within `runSpeed`, so the body's velocity bounds each step. Every other
  rise needs a contact, and the bound holds only where none can happen in the ticks left, checked against the live Box2D
  world: no static box with a top or bottom face in the vertical reach (the ground and pop rays start inside the player's own
  collider, which Box2D keeps out of the solids it collides with: checked on the contact masks and the collider's overlap
  now; so they find only a top 18–40 u under the transform, and the step-up ray a top in y−33..y+20), no solid within the
  wall rays' and ray3's reach on a tick their gate can open (`Velocity.y` 200 or less, or
  `dashActive`: its end tick is fixed by `dashFramesRemaining`), and no trigger but a spike, moving body or non-box collider
  in reach at all; every threshold is widened by 2 u. A state whose collider top stays at or under the box's bottom on every
  tick is cut. The height prune: its highest reachable y (the ballistic arc plus every jump and boost it has or a landing
  refills) is below the finish box (a lab with a spring has none: a spring's launch isn't in it); the time prune: too far
  from the box to reach it in the ticks left (the game's own 100 u/step max translation is the most any input can move
  the player, 110 on a lab with a spring for its 10 u push). `--check-bound` cuts nothing with the free-flight
  bound and instead checks it: each state against the lowest bound any of its ancestors gave for its tick (and each finish
  against the box), reported as `BOUND VIOLATED` lines; `--check-depth N` expands only to tick N (the bounds still run to

  (a new jump or dash press on 1 input in 8), each state checked against every earlier state's bound, and reports the
  tightest slack. The log counts, per tick, the states expanded and each prune, and which reasons left states without the
  free-flight bound. States are deduplicated by a key of the state; the default key is coarse (1 u position, 10 u/s velocity, 1 u counters)

## Humanize

A best comes out of the search full of tick-exact and analog-exact inputs, most of which don't matter.
`humanize <start-trace> <best.json>` writes `<best>-human.json`, a same-time version that is easier to play,
`<best>-human.md`, which says how much slack each of its inputs has, and `<best>-human.slack.json`, the same slack
structured for the studio (below). `solve` does this for every new best on one
background thread (a newer best replaces one still waiting; the last one is finished before `solve` exits, on the
solve's `--threads` workers once the search has stopped, since its tolerance runs are independent).

Simplify: greedy passes, repeated until none changes anything. A change stays only if the run still finishes offline in
the same time (the course timer, or physics ticks for a bonus or transition), in no more physics ticks from the run
start, and on the forced path (`--via`/`--avoid` plus `Cli\forced-paths.json`, as in `solve`).

- A partial `x` goes to full tilt, else to rest.
- A partial that has to stay goes to the middle of the band of partials (0.3..0.8 in steps of 0.05) that work.
- A stick run takes its neighbour's value, which removes a stick change. A vertical goes back to rest first, and leaves
  rest only to fill a gap in one hold.
- Presses and dashes that change nothing are dropped. Dropping a press after the button was up drops its hold and
  the release that ended it.
- Presses and dashes move as early as they still work (the buffer).

Report: every input of the human version (stick change, jump press, release, dash) is moved up to 6 input ticks
either way, one tick at a time, until it stops working. A stick run also tries the other stick values: `x` full
either way, rest, and every partial on its side; `y` −1, 0, 1. Each input is `exact` (one tick only, or one partial
value only), `free` (no limit found either way, any value), or `window N`. The report counts exact inputs in the
best and in the human version, and lists what changed. Ticks are input ticks (dash and spring ticks take none).

`<best>-human.slack.json` is that report as data: `course`, `capabilities`, `source`, `human`, `time`, `runTicks`, the
counts `exact`/`exactBefore`, and one entry per input of the human version (`tick`, `end`, `kind` (`stickX`, `stickY`,
`press`, `release`, `dash`), `value`, `class`, `window`; `end` is the tick after the input's last). The studio's
**Timeline** tab draws it as the human version's frame timeline (**Human version · input slack**, every frame colored by
the slack of the input on it: red `exact` — practice that one — amber `window`, violet `band`, green `free`), served by
`POST /api/enginesim/slack {name}` with the human version's `ticks`.

The human version is never a record and never replaces the best: it goes to its own file, a change that made it slower
in time or physics ticks is never kept, and the plugin never judges a `-human.json` file. The studio plays the newest one
for the category with "Play human version" (`/api/enginesim/play {human: true}`), and "Walk route" plays the newest
one as fast as the selected route (same game time for a category route, same physics ticks for a farm route) in its
place; while it plays, the studio's top bar turns violet with a HUMANIZED badge (`/api/state` `humanPlayback`).

## Rules

- Nothing here changes how the game or the plugin behave; the plugin only gained read-only export endpoints and
  `submit`, which judges an offline best in turbo: the game replays the candidate's inputs on its own turbo engine
  (`Solver.cs` `Evaluate`), and the run is saved only when it beats the saved route's time or the farm route's
  `runTicks` (`EngineSimBridge.Judge`) — the same check every waiting `offline-best\` file gets.
- A method goes into `cuts.txt` only if it is presentation or real-time-only work that turbo never sees within a run.
- Invokes: every script's `Invoke` fires on ticks, in turbo and here.
- Fidelity is measured, not assumed: `replay` must report every tick identical on the trace corpus.

  trigger the pair wasn't touching also enters when its sensor contact touched at the start of the step (a wall jump's

## Memory

A snapshot (for branching) is ~25 KB on the VMAN route: the broadphase tree stores only nodes that
differ from a shared base, the pair/move buffers only their live prefix, and unchanged fixture records are shared
between snapshots. So are the field captures of the touched scripts and the courses: a capture reuses the previous
one's array while none of its fields changed (`Simulation.CaptureShared`, `FieldState.Matches`) — before, every touched
script's capture was copied into every snapshot, and a VMAN search with 28 workers ran out of memory within minutes
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Field captures copied into every snapshot*). `solve` prints heap and working set every 10 s, and the host
runs with `System.GC.HeapHardLimit` at 70 GiB, so a leak throws OutOfMemory instead of paging the machine.

A best's replay (on every new best, adopted best and plateau drift) keeps a snapshot every 16 input ticks, not every
tick (`OfflineSolver.StateEvery`); a mutation resumes from the one at or before its first changed tick (snapshotting
every tick left the workers waiting on the GC most of the time:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *Snapshot every tick stalled the workers*). A mutation's replay starts from the snapshot it resumed from and
copies the best's record before it (`OfflineSolver.Worker.Replay.CopyPrefix`): same inputs up to there, same states.

The explore archive is one map shared by every worker (`OfflineSolver._archive`): a cell is its input prefix (the run's
inputs and the tick), the arrival time, the picks and the cell it was explored from (`Parent`), never a snapshot. A
snapshot belongs to one worker's `Simulation` (it holds that world's objects and fixtures), so each worker keeps its
own snapshots (`StatesPerWorker`: half of the GC heap limit or of physical RAM, whichever is lower, over 32 KB per
snapshot, split across the workers), evicted by
the draw pool's pick weight first and recency second (a queue record older than the entry's last use is skipped), so the
frontier's hot cells stay through a wide draw's churn
(plain LRU let them go). A cell is owned by the worker that last kept its snapshot (`Cell.Owner`); a worker draws from
its own cells with probability min(0.95, 0.9 × workers × own weight / total weight), else from every cell, with the same
weights, so the draws summed over workers stay close to one global draw while most picks hit a cached snapshot. A worker
that picks a cell it has no snapshot for replays the cell's inputs from its nearest
ancestor it has one for (from the start when none), and keeps a snapshot of every cell on that path. So an explore
draws up to three cells and takes the first it has a snapshot for (`CachedDraws`): on C4 WJ_DS_DJ with 32 threads the
replays were ~23% of all ticks simulated before cells had owners (each worker used to keep its own archive with a snapshot per cell:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *A snapshot per cell per worker*). `solve` and `fulltas` print the archive's size, the share of picks whose snapshot was
cached and the ticks spent replaying (`ArchiveStatus`).

The states get half the heap; everything else has to fit in the other half, and the cells' inputs are most of that. A
cell's inputs (its run's, shared by every cell the run filed) are run-length stored (`InputRuns`, ~25 equal ticks a
run on a saved archive), and so are a loaded or exported archive's sources (`Memory.Source.Inputs`): `Export` trims a
source without copying it, and the archive loads straight into runs. As `List<InputTick>` (68 bytes a tick, and every
explore run copies its cell's 1,000-2,000-tick prefix on Area 2's courses) they outgrew the states: resuming Course 9
WJ_DS_DJ_BS from a 147k-cell archive with 16 threads under a 20 GiB heap, the loaded archive took 3 GB, the explore
cells' lists grew ~1.5 GB every 10 s, and `Export`'s copy of every source threw OutOfMemory after 2.5 minutes (the
committed engine did the same, so no engine change caused it). Run-length, the same solve's live heap stays ~2-4 GB
over the states' budget (inputs ~1.3 GB at 200k cells, still growing with the archive) and every export succeeds; a
heap dump puts the rest mostly in the states' broadphase trees.

The archive has a budget too: a quarter of the same memory (`OfflineSolver._archiveBudget`; the states keep their half,
the rest is the worlds, the replays, exports and the GC's room). Its bytes are counted as cells are filed, replaced and
evicted (`Count`): each cell (the `Cell`, its dictionary node, its slots in every worker's draw pool arrays:
`CellBytes`) and a run's inputs while one of its cells is in the archive (`InputRuns.Cells`, `InputRuns.Bytes`). Over
budget, the filing worker evicts the cells with the lowest pick weight (its `Weight`, as its state eviction uses) down
to 7/8 of it, then takes every removed cell (evicted, or replaced since) out of the live cells' `Parent` chains; the
workers rebuild their draw pools and drop their states for removed cells. Under budget none of this changes a
decision, so a search that stays under it is the search it was. The progress line shows the archive's MB (and the
cells evicted). A loaded archive's sources are dropped once each worker has restored its share (the solver keeps only
its runs count and plateau routes). The budget follows the heap limit: under the CLI's default 70 GiB the states alone
may take 35 GiB (Course 6 WJ_DS_DJ_BS_ORB_ZIP_OM with 4 threads grew ~20 MB/s into a 12 GB kill that way, filling its
state cache as designed), so a solve that has to stay under a cap sets `DOTNET_GCHeapHardLimit` to it. Below ~2 GB
the fixed part (tech-graft patterns, worlds) doesn't fit: a 1 GiB C6 solve runs out of memory before its first explore,
on the old build as on this one. Measured on C6 WJ_DS_DJ_BS_ORB_ZIP_OM (2 threads, 3 GiB heap): a state is ~55 KB, two
thirds of it the broadphase tree's delta (~670 of 12,000 nodes differ from the shared base; 25% of 32-node chunks do,
so chunked sharing would be larger); live heap after a full GC stays 1.65-1.76 GB for 7 minutes while the archive grows
~13 MB a minute (81 MB of inputs at 71k cells); with the archive's budget forced to 40 MB the count holds 35-39 MB (a
heap walk agrees: 34 MB of inputs plus 24.6k cells) through 131k evictions in 6.5 minutes.

A Full-TAS run's goal-boundary states also persist to disk (`SnapshotStore`, `SnapshotIndex`): when the run first
reaches goal k, or a better arrival does, its state goes to `archive\fulltas-<run>\states\`, keyed by the hash of the
run's inputs up to it and dropped with the archive (the run's `start.key`). A solve's windows start from the stored
state at their prefix's end instead of replaying the run up to there, and a cell replays its prefix from the later of
its worker's own ancestor and a stored goal state on the same inputs (`ArchiveStatus` counts those resumes). A state is
a byte-for-byte value walk of the snapshot (`SimSnapshot`'s fields, world objects as their export's ids, fixtures as
their collider and shape), so a restored one continues exactly as the replayed one; what the walk can't write (a type
it doesn't know) just isn't stored and the run replays to it as before. On the VMAN route a state is ~1.6 MB on disk
(the broadphase tree's shared base is a full copy per state) against ~25 KB in memory.

The physics backing those states rely on: a fixture's shape fingerprint is a plain deterministic mix
(`PhysicsWorld.FingerprintOf`), and `Pristine` is the fixtures the world loaded (`ColliderState.Tracked` marks the
rebuilds that join `_changed`), so a restore puts a collider its snapshot doesn't list back to what the world loaded
(fixtures, scale, layer, contact mask). Storing states across runs needed both
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *Persisted states across runs*). The static bodies' fixture state
is numbered from a random base per world (`b2World.m_staticEpoch`, which lets a load skip them), so a state another
process saved can't match the number by chance. A simulation restores only the active/enabled/layer toggles it has
tracked since load. A stored state's toggles can name objects the loading simulation never changed (a block swap's
tilemap collider under the `blueSpikes` composite), so the load tracks those first, from their loaded values
(`Simulation.TrackToggles`), before it applies them and rebuilds the colliders the state lists. `Simulation.Fingerprint`
hashes only toggles that differ from the load, so a state hashes the same whatever toggled before it. Before, 5 of
Course 7's 10 route snapshots couldn't be stored, and the other block-swap courses lost some too
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *A stored state lost the toggles its simulation never made*).

A restore gives back exactly the physics state its capture saw, whatever the simulation ran before: Box2D's (bodies,
fixtures and proxy ids, the contact list in order with each contact's flags, manifold and touch order, the touch
counter, the move and pair buffers, every broadphase tree node) and the host's (each collider's fixtures, scale, layer
and contact mask, the player's colliders' too, the touching pairs, the syncs, teleports, rebuilds and rescales
pending for the next step, and every other body's transform: `PhysicsSnapshot`). Before, the player's box kept the last
run's contact mask and a restore kept the last run's pending flags, so an edge could end differently after other edges
([`docs/fidelity-log.md`](../docs/fidelity-log.md), *A restored run depended on the runs before it*); and a zip mover
kept the last run's transform, which its pending sync then moved the body to (*A restore left the other run's body
transforms*). `determinism
<trace> <route> [--edges N] [--seed S] [--passes P]` checks it (`Cli/Determinism.cs`): 10 snapshots along the route
(both sides of its rebases), a fixed set of N edges from them (default 300; 17-150 ticks of the route's inputs, near
the snapshot or from anywhere later), every third capturing a state halfway that a child edge runs from later in the
pass, run in order, then in P-1 shuffled orders, then in a second process with another shuffle. Every restore's
physics digest (`PhysicsWorld.StateDigest`, `b2World.StateDigest`: all of the above, bit for bit, the same in every
process) must equal its capture's, every run's end state must be the same in every order and process, each pass-0
halfway capture, restored after other runs and continued on its edge's own inputs, must end in the edge's end state,
and the route snapshots stored as bytes (`SnapshotStore`, all saved before the fresh simulation is made) and loaded
into a fresh simulation must restore the same state and end their edges the same. It prints `DETERMINISTIC` (exit 0)
or the first differences; `IGTAP_DETERMINISM_DUMP=<edge>` writes that edge's halfway capture and its restore as text
to diff. VMAN 45.20, 44.92 and 48.18 with 600 edges: every restore equal to its capture (2,256-2,286 each), 800 of 800
runs identical across orders and processes (the build before: 21 restores off and 5 runs different on 45.20). Course 7
`WJ_DS_DJ_BS_ZIP` (`7_wjdsdjbszip-7.96`): 1,137 of 1,137 restores, 79 of 79 continuations (the build before: 467
and 78) and 10 of 10 stored snapshots (the build before: 5). Courses 8, 10, 14 and 15, zip and orb, are DETERMINISTIC
with every route snapshot stored.

A capture after a restore shares the restored snapshot's changed-collider list until a collider is rebuilt
(`PhysicsWorld._changedCapture`), and each body's record until the body changes (a load seeds `b2World.m_savedBodyRecs`).
The broadphase tree's delta is taken against the base of the snapshot the tree was last loaded from or saved as, not the
newest base: a capture after a restore across the rebase compared the whole tree (5,800 nodes on VMAN) and copied a new
base every time. On the 48.18 route (`enginebench`, restore and capture of the snapshots at inputs 200-1650, two runs
each) a restore plus capture took 113-218 µs (up to 73 KB), now 22-59 µs; the physics capture alone 104 → 7 µs; 17-tick
branches ~6-8% faster, branches across the rebase unchanged. Trigger dispatch keeps each trigger contact's
`b2TestOverlap` with the two bodies' transforms bit for bit (`b2Contact.m_overlap`): a trigger on a body at rest isn't
tested again, 94% of the tests hit and `CollectTouching` takes 1.8 µs a step instead of 3.0. Results are
byte-identical: the 502-trace verbose replay corpus and the VMAN 45.20 (2260 ticks), 44.92 (2246) and 48.18 (2409)
checks.

Scene queries (raycasts, point tests, `Collider2D.Distance`) read static shapes from a grid built once over the world. A
collider whose static fixtures change, or whose static body moves, is regridded alone at the next query (the whole
grid used to rebuild on each change, with the LOH garbage stalling every worker:
[`docs/fidelity-log.md`](../docs/fidelity-log.md), *Grid rebuilt on every change*). The cells sit in one flat array
(a counting sort over the shapes, `PhysicsWorld.Grid`); a regridded shape goes to a per-cell side list and its old slot
is skipped until the next layout. A change of more than 1024 shapes (a FloatingOrigin rebase rebuilds every body-less
collider; a restore across one moves them all back), or a shape leaving the grid, lays out another grid, and the two
grids laid out before are kept (with their arrays, reused by the next layout): when every collider is back where one of
them holds it (checked collider by collider; a rebuilt collider whose new shapes are the held ones bit for bit counts,
and the slots take its new fixtures), that one is taken back instead (`_spareGrids`). A layout also covers where a static body's pending sync will move it, so a rebase's body move regrids
in place. The broadphase pairs a moved proxy of a non-dynamic body only with the dynamic bodies' proxies when more than
64 moved (`b2BroadPhase.UpdatePairs`): Box2D drops every pair without a dynamic body anyway (`b2Body.ShouldCollide`),
and the kept pairs are the same and sorted the same. On VMAN (5811 static shapes, ~480k cells, rebase near goal 16)
each run crossing the rebase had cost ~45–110 ms of grid layouts and static-static pairing; it now costs ~15 ms
(2026-09-29, `enginebench`: 120-tick branches from input 1000 of the 48.18 route, 21 → 66 edges/s; every other run
unchanged). Results are byte-identical: the 502-trace verbose replay corpus and the VMAN 48.18 (2409 ticks) and
45.20 (2260 ticks) checks.
